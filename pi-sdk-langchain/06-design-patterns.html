共通要件

題材は規程文書レビューとする。入力文書とpolicyを読み、issue一覧とverdictを構造化出力する。filesystem全体、shell、任意networkは使用しない。

要件契約

出力ReviewResult schema

const ReviewResult = z.object({
  verdict: z.enum(["PASS", "FAIL"]),

    severity: z.enum(["critical", "medium", "low"]),
    location: z.string(),
    message: z.string(),
  })),
});

パターンA: Pi SDKを薄いworkerとして使う

host applicationがartifact、timeout、credential、publishを所有し、Piは一回のmodel-tool loopだけを実行する。

TypeScript
async function runPiReview(request: ReviewRequest) {
  const workspace = await stageDeclaredInputs(request);
  const model = getExactModel("provider", "model-id");
  const tools = createArtifactTools(workspace, request);

  const { session } = await createAgentSession({
    model,
    thinkingLevel: "high",
    customTools: tools,
    sessionManager: SessionManager.inMemory(),
    resourceLoader: emptyLoader,
  });

  assertExactRuntime(session, {
    modelId: "model-id",
    tools: ["read_input", "submit_result", "write_review"],
  });

  const events = collectPiEvents(session);
  await withDeadline(() => session.prompt(buildPrompt(request)));
  await session.agent.waitForIdle();

  const submitted = requireSubmittedResult(events);
  ReviewResult.parse(submitted);
  await validateStagedArtifacts(workspace);
  return atomicPublish(workspace);
}

この構成では業務の正本はhostにある。Pi sessionをresumeしない。再試行は新attemptとしてhostが作る。

向く条件

  • 既存applicationにworkflow/stateがある。
  • model/tool/promptを完全固定する。
  • 一回のtaskが短命。
  • observabilityを自前基盤へ統合する。

パターンB: LangChain agentとして構築する

model integration、tool schema、structured output、middlewareをLangChainへ任せる。

TypeScript
const authMiddleware = createMiddleware({
  name: "artifact-authorization",
  wrapToolCall: async (request, handler) => {
    assertAllowedArtifact(request.toolCall.args.artifactId);
    return handler(request);
  },
});

const reviewer = createAgent({
  model: exactModel,
  tools: [readInput, writeReview],
  responseFormat: ReviewResult,
  systemPrompt: REVIEW_PROMPT,
  middleware: [authMiddleware, auditMiddleware],
});

const result = await reviewer.invoke({
  messages: [{ role: "user", content: task }],
});
const review = ReviewResult.parse(result.structuredResponse);

構造化出力が最終responseでよい場合は短い。成果物fileの書込を完了条件にするなら専用submit toolまたはagent終了後のapplication validationを追加する。

向く条件

  • 複数providerを比較する。
  • typed responseが主成果物。
  • middlewareを横断再利用する。
  • LangSmithでtrace/evaluationする。

パターンC: LangGraphで工程を分離する

調査、レビュー、機械検証、承認、公開を別nodeへ分け、各nodeの入力・出力をstateへ保存する。

TypeScript
const ReviewState = Annotation.Root({
  documentId: Annotation<string>(),
  sourceHash: Annotation<string>(),
  draftReview: Annotation<ReviewResult | null>(),
  validation: Annotation<ValidationReceipt | null>(),
  approved: Annotation<boolean>(),
});

const graph = new StateGraph(ReviewState)
  .addNode("load", loadAndPinSource)
  .addNode("review", runReviewAgent)
  .addNode("validate", validateReview)
  .addNode("approve", humanApproval)
  .addNode("publish", idempotentPublish)
  .addEdge(START, "load")
  .addEdge("load", "review")
  .addEdge("review", "validate")
  .addConditionalEdges("validate", s =>
    s.validation?.ok ? "approve" : "review")
  .addConditionalEdges("approve", s =>
    s.approved ? "publish" : END)
  .addEdge("publish", END)
  .compile({ checkpointer });

agentはreview nodeの内部に置く。graph自体に全判断をLLM化しない。hash計算、schema validation、publishは決定論的nodeにする。

向く条件

  • 工程が複数あり差し戻しがある。
  • 人間承認が数時間以上続く。
  • process再起動から再開する。
  • 各工程のprovenanceを残す。

Worker process隔離

SDKを同一processへ埋め込むとtool、extension、provider adapterの例外とmemory leakがhostへ波及する。productionでは専用worker processを使う価値がある。

境界ParentWorker
credential必要keyだけallowlistin-memoryで使用
filesystemstagingを作成stagingだけ参照
timeoutprocess killAbortSignalを受ける
protocolstrict JSON検証stdoutへ単一envelope
publish検証後にatomic publish直接publishしない

LangChainもPiも同じworker patternを使える。framework選択とprocess boundaryは別の設計判断である。

Artifact契約

会話履歴ではなく型付きartifactで工程を接続する。

JSON
{
  "artifactId": "review-result",
  "schemaId": "review-result/v1",
  "path": "staging/review.json",
  "contentHash": "sha256:...",
  "inputHashes": ["sha256:...", "sha256:..."],
  "producer": {
    "runtime": "pi-sdk",
    "model": "exact-model-id",
    "attemptId": "attempt-17"
  }
}

artifactがあれば、modelを変えても工程境界を維持できる。resume時は現在の入力hash、schema、runtime profileが一致する場合だけ再利用する。

テスト戦略

テスト内容
Contracttool input/output、artifact schema
Runtime identityprovider/model/tool集合の完全一致
Mutation余計なtool、model差替、path escapeを検出
Failuretimeout、cancel、rate limit、malformed output
Idempotency同一publish keyで二重副作用なし
Golden固定inputに対する構造・重要論点
Evaluation実データ集合で品質・費用・latency

LLM出力全文の完全一致testは脆い。必要論点、schema、禁止操作、tool trace、費用上限を検査する。

反パターン

  1. 巨大agent一体化 — 収集、判断、公開を一sessionへ入れる。
  2. promptだけの権限制御 — toolを渡したまま「使うな」と書く。
  3. silent fallback — model失敗時に別modelへ自動切替する。
  4. sessionを業務DB化 — durable stateと会話履歴を混同する。
  5. 未検証publish — modelの最終文をそのまま本番へ書く。
  6. 全例外retry — credential欠落やunknown dispatchまで再試行する。
  7. framework二重化 — 既存workflow engineの上へ別graphを無目的に重ねる。
設計原則

LLMに任せるのは意味判断。identity、schema、hash、path、retry、publishは決定論的コードで管理する。

理解度チェック

Pi SDK版でhostが所有すべきものは何か。
artifact、credential、timeout、runtime identity、validation、publish、attempt。
LangGraph node内にagentを置く利点は何か。
model-tool反復とworkflow state transitionを分離できる。
artifactを会話履歴より優先する理由は何か。
schema、hash、producer、input lineageを機械検証できるため。
