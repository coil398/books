LangChainの位置づけ

LangChainは単一agent loopだけのlibraryではない。model providerの共通interface、messages、tools、structured output、middleware、retrieval、LangGraph runtimeへの接続を一つの開発体験にまとめる。

現在の高水準入口はcreateAgent()である。内部ではLangGraphを用いてmodel nodeとtool nodeの反復を構築する。利用者はgraphを意識せずagentを開始でき、必要になればmiddlewareやLangGraphへ降りる。

設計上の立場

Pi SDKがsessionを直接握るのに対し、LangChainはLLMアプリの共通部品と標準的なagent構造を提供する。

Model abstraction

複数providerを共通のChatModelとして扱えることがLangChainの基本価値である。文字列指定、provider package、model instanceのいずれかからagentへ渡す。

TypeScript
import { createAgent } from "langchain";
import { ChatOpenAI } from "@langchain/openai";

const model = new ChatOpenAI({
  model: "exact-model-id",
  temperature: 0,
  maxRetries: 0,
});

const agent = createAgent({
  model,
  tools: [lookupRecord, submitResult],
  systemPrompt: SYSTEM_PROMPT,
});

共通interfaceはprovider差を消し切るものではない。reasoning、cache、tool use、native structured output、usage metadataはprovider固有能力として残る。抽象化の利点は同一アプリ構造を維持できることであり、モデルが同じ挙動になることではない。

createAgentの実行モデル

  1. stateからmessagesをmodelへ渡す。
  2. modelがtool callを返せばtool nodeへ移る。
  3. tool resultをmessagesへ追加する。
  4. 再びmodelへ戻る。
  5. stop conditionまたは最終responseで終了する。

この構造は第1章のagent loopそのものだが、LangChainではmiddleware、state schema、context schema、responseFormatを統合できる。

入力役割
model意思決定を行うChatModel
toolsモデルが呼べる能力
systemPrompt固定またはmiddlewareで動的生成
responseFormat最終構造化出力
middlewaremodel/tool前後、状態、guardrail
contextSchemarunごとの不変context

構造化出力

LangChainはprovider native structured outputを使うProviderStrategyと、schemaをtoolとして提示するToolStrategyを抽象化する。model能力に応じて方式を選び、最終結果をstateのstructuredResponseへ格納する。

TypeScript
import { z } from "zod";

const Review = z.object({
  verdict: z.enum(["PASS", "FAIL"]),
  issues: z.array(z.object({
    severity: z.enum(["critical", "medium", "low"]),
    message: z.string(),
  })),
});

const reviewer = createAgent({
  model,
  tools: [readDocument],
  responseFormat: Review,
  systemPrompt: "Review the document against the policy.",
});

const result = await reviewer.invoke({
  messages: [{ role: "user", content: "Review document-42" }],
});
Review.parse(result.structuredResponse);

便利だがoutput repairやstrategy選択が追加model callを生む場合がある。API回数を厳密に制御する用途では、使用strategyとretry挙動を固定する。

Middleware

MiddlewareはLangChainの強力な拡張点である。model call前後、tool call前後、agent開始終了に介入し、prompt、model、tools、state、errorを変換できる。

種類用途危険
beforeModelcontext整形、prompt追加最終promptが追跡困難
wrapModelCall動的model、retry、cachesilent model switch
wrapToolCall認可、logging、error変換tool結果の意味変更
afterModelguardrail、検証追加callやrepair
summarization長い履歴の圧縮元履歴との差分
human-in-the-loop高リスクtool承認checkpoint設計が必要

Middlewareは「余計な層」ではなくLangChainの主要な価値である。ただし厳格systemでは、どのmiddlewareがmodel、tools、messagesを変更したかをmanifest化する。

Memoryとcontext

LangChainは短期memoryをagent state、長期memoryをstore等で扱う。contextSchemaはrun単位の不変依存を型付きで渡す。messagesだけに全情報を詰め込む設計を避けられる。

  • 短期memory: 同一threadのmessagesとstate。
  • runtime context: user ID、tenant、権限、設定。
  • 長期memory: threadを越えて検索するprofileやfacts。
  • retrieval: 必要時に外部knowledgeを取得するtool。

memoryは自動的に真実にならない。書込policy、expiration、source、conflict resolution、削除要求を設計する。

Tools

tool helperでname、description、schema、executeを定義し、runtime contextやstateへアクセスできる。tool数が多い場合はmiddlewareで動的に絞り込める。

TypeScript
import { tool } from "langchain";
import { z } from "zod";

const readTicket = tool(
  async ({ ticketId }, runtime) => {
    authorize(runtime.context.userId, ticketId);
    return ticketStore.read(ticketId);
  },
  {
    name: "read_ticket",
    description: "Read one authorized support ticket.",
    schema: z.object({ ticketId: z.string() }),
  },
);

tool schemaを狭くする原則はPiと同じである。LangChainが権限を代行するわけではなく、認可はtool implementationまたはmiddlewareで行う。

Observability

LangSmithと統合するとmodel call、tool call、latency、token、trace、dataset evaluationを追跡できる。大規模運用でLangChainを選ぶ最大の理由になり得る。

一方、framework外の独自処理も同じtraceへ結ぶにはinstrumentationが必要である。observabilityを採用理由にするなら、agent以外のworkflowも含むtrace設計まで確認する。

評価

強い点
  • provider統合が広い
  • typed structured output
  • middlewareが豊富
  • LangGraphへ自然に拡張
  • LangSmith運用
弱い点
  • 抽象化層が多い
  • 最終requestの追跡が必要
  • version更新面積が広い
  • provider差は残る
  • 簡単なloopには過剰
適する設計
  • 複数provider
  • API/Web service
  • typed output中心
  • middleware再利用
  • 組織的観測・評価
誤った期待

LangChainを入れれば高品質になるわけではない。実装速度、統合範囲、運用標準化が価値であり、model判断そのものは別問題である。
