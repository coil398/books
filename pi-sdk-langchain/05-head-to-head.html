System promptの制御

Pi SDK

最終session stateのsystem promptを読み、置換できる。Resource Loaderを閉じればambient contextを排除しやすい。一方、標準coding agentの既定promptを無指定のまま使えばcoding用途の前提が残る。

LangChain

systemPromptを指定でき、middlewareがrequest直前に生成・変更できる。柔軟性が高い反面、複数middlewareがあると最終requestをtraceで確認する必要がある。

LangGraph

単一system promptという概念を強制しない。nodeごとにmodelとpromptを完全分離できる。工程間の情報をstate contractで渡せる。

勝者

単一agentの透明性はPi SDK。動的policyと再利用はLangChain。工程別完全分離はLangGraph。

状態、再開、長時間実行

ここは明確にLangGraphの領域である。Pi sessionの保存は会話の継続には使えるが、業務工程のdurable checkpoint、branch、human interruptとは異なる。LangChain agentはLangGraph上で動くためthread stateを使えるが、複雑な工程では直接graphを設計した方が境界が明確になる。

Provider抽象化

LangChainは対応provider数と統一interfaceで優位に立つ。Piも主要providerとcustom providerを扱えるが、ecosystemの広さではLangChainが上である。

ただしmodelを一つへ固定するsystemでは広いprovider抽象化は価値にならない。むしろalias、fallback、capability negotiationを閉じる方が重要になる。この場合、Pi SDKの直接性が有利になる。

provider非依存の誤解

共通interfaceは交換コストを下げるが、同じ品質・同じtool semantics・同じstructured outputを保証しない。

Observabilityと評価

組織規模でtrace、dataset、online evaluationを統一したい場合、LangSmith ecosystemは強力である。Piではeventを自前のOpenTelemetry、DB、ログ基盤へ流す設計になる。

運用要件優位
既存observabilityへ最小eventを流すPi SDK
agent traceをすぐ可視化LangChain + LangSmith
graph stateとcheckpointを追跡LangGraph + LangSmith
vendor依存を抑えるPi SDK + 自前telemetry
evaluation datasetを組織共有LangSmith

判定

Pi SDKを選ぶ
  • 単一agent loopが必要
  • tool/prompt/modelを厳密固定
  • 既存state machineがある
  • 依存を薄くしたい
LangChainを選ぶ
  • provider統合を広く使う
  • typed outputを短く実装
  • middlewareを再利用
  • LangSmithを使う
LangGraphを選ぶ
  • 複数工程・分岐
  • durable execution
  • 人間承認・長時間待機
  • checkpointから再開

一般的な優劣はないが、要件ごとの正解は曖昧ではない。単一loopへLangGraphを入れるのは過剰であり、数日待機workflowをPi sessionだけで管理するのは不足である。
