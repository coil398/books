選定と運用

要件から一意に選び、PoC、移行、version pin、監視まで実務手順へ落とす。

難易度中〜上級

選定規則

次の順序で判定する。機能デモの印象から始めない。

  1. processを跨ぐstateが必要か。 必要ならLangGraph。
  2. 人間承認、分岐、並列、差し戻しが主題か。 主題ならLangGraph。
  3. 単一agent loopだけ必要か。 既存基盤へ埋めるならPi SDK。
  4. 複数provider、structured output、middlewareを短期間で揃えるか。 LangChain。
  5. terminal製品を拡張して使うか。 Pi CLI/Packages。
最短の判断

workflowを持っているならPi SDK。workflowを持っておらず長時間stateが必要ならLangGraph。一般的なLLMアプリを早く構築するならLangChain。

PoCの作り方

frameworkごとに別taskを試してはいけない。同じinput、model、tool contract、timeout、評価datasetを使う。

Evaluation manifest
{
  "dataset": "review-set/v1",
  "runs": 100,
  "model": "exact-model-id",
  "maxTurns": 12,
  "timeoutMs": 180000,
  "tools": ["read_input", "write_output", "submit_result"],
  "fallback": "forbid",
  "metrics": [
    "task_success",
    "schema_pass",
    "tool_policy_pass",
    "latency_p95",
    "input_tokens",
    "output_tokens",
    "manual_review_score"
  ]
}

PoCで変えてよいもの

  • framework固有のsession/agent構成。
  • structured output方式。
  • event/trace収集。

変えてはいけないもの

  • model ID、reasoning level、input snapshot。
  • 許可toolsと業務schema。
  • retry/fallback policy。
  • 成功判定。

移行戦略

LangChainからPi SDK

  1. toolsをframework非依存interfaceへ切り出す。
  2. responseFormatをsubmit toolまたはapplication validatorへ移す。
  3. middlewareの責務をprompt、tool wrapper、host policyへ分類する。
  4. messages/sessionをPi形式へ変換する。
  5. trace eventを既存observabilityへ接続する。

Pi SDKからLangChain

  1. custom toolsをLangChain tool schemaへ変換する。
  2. final submitをresponseFormatまたはtool strategyへ移す。
  3. event hookをmiddleware/LangSmithへ接続する。
  4. resource loaderの内容をsystem prompt/contextへ明示移植する。

単一agentからLangGraph

  1. 工程をnodeへ分割する。
  2. 会話履歴と業務stateを分離する。
  3. artifact schemaとReducerを定義する。
  4. 副作用nodeへidempotency keyを導入する。
  5. checkpoint migrationとinterrupt UIを用意する。
移行時の禁止事項

旧frameworkと新frameworkを同時に正本にしない。shadow runで比較し、切替点を一つに固定する。

Version管理

LLM frameworkはAPIだけでなくprompt、tool schema、provider adapter、retry semanticsが変わる。lockfileだけでなくruntime manifestを保存する。

Runtime manifest
{
  "runtime": "pi-sdk",
  "runtimeVersion": "exact-version",
  "providerAdapterVersion": "exact-version",
  "modelId": "exact-model-id",
  "thinking": "high",
  "toolSchemaHash": "sha256:...",
  "systemPromptHash": "sha256:...",
  "resourceManifestHash": "sha256:..."
}
  • semver rangeではなくexact versionをproductionでpinする。
  • upgradeは固定datasetで再評価する。
  • model aliasではなくresolved model IDを記録する。
  • prompt、tool schema、middleware/extension manifestをhash化する。
  • rollbackできるartifactを残す。

運用手順

  1. run開始時にruntime manifestとinput hashを確定する。
  2. model/tool eventsをattempt IDへ紐付ける。
  3. timeout/cancel時はpublishを禁止する。
  4. retryは新attemptとして発行する。
  5. fallbackは原則禁止し、必要なら別profileとして明示する。
  6. success後にschema、artifact、policy、costを検証する。
  7. 日次でfailure分類、週次でquality drift、月次でupgrade候補を評価する。

  • 未許可tool
  • model mismatch
  • credential error
  • cost急増
日次
  • failure rate
  • latency p95
  • schema error
  • retry回数

  • drift sample
  • tool policy
  • dataset追加

最終結論

Pi SDKは、model-tool loopを既存systemへ薄く埋め込み、最終promptとtool集合を直接制御したい場合の第一選択である。

LangChainは、複数provider、typed output、middleware、observabilityを短期間で標準化したい場合の第一選択である。

LangGraphは、長時間state、分岐、承認、checkpoint、process再起動を要件に含む場合の第一選択である。

選定を一文で固定する

単一loopはPi SDK、LLMアプリ部品はLangChain、durable workflowはLangGraph。
