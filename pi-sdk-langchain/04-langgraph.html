なぜLangChainと別に扱うのか

LangChain agentはLangGraph上で動くが、LangGraph自体はより低水準である。modelを一度も呼ばない決定論的node、外部job、人間承認、長時間待機を同じ状態遷移として表せる。

中心は「賢いagent」ではなく、入力stateに対してnodeが部分更新を返し、edgeが次のnodeを決める実行モデルである。

責務

Pi SDKとLangChainが主にmodel-tool loopを提供するのに対し、LangGraphは複数工程のstate transitionとdurabilityを提供する。

StateGraph

StateGraphでは、共有state、node、edge、start/endを宣言しcompileする。

TypeScript
import { StateGraph, START, END, Annotation } from "@langchain/langgraph";

const State = Annotation.Root({
  request: Annotation<string>(),
  sources: Annotation<Source[]>({ reducer: (a, b) => a.concat(b), default: () => [] }),
  draft: Annotation<string | null>({ default: () => null }),
  approved: Annotation<boolean>({ default: () => false }),
});

const graph = new StateGraph(State)
  .addNode("research", researchNode)
  .addNode("draft", draftNode)
  .addNode("approve", approvalNode)
  .addEdge(START, "research")
  .addEdge("research", "draft")
  .addEdge("draft", "approve")
  .addConditionalEdges("approve", s => s.approved ? END : "draft")
  .compile({ checkpointer });

nodeの戻り値はstate全体ではなく部分更新でよい。複数branchが同じfieldを更新する場合はReducerが統合規則を決める。

StateとReducer

設計対象悪い例良い例
state粒度巨大なuntyped object工程境界を表すtyped fields
message全履歴を無制限append専用reducerとtrim policy
artifact本文だけ保存ID、hash、schema、producerを保存
並列統合最後に書いた値で上書きReducerで決定的に統合
外部参照可変URLだけ保存snapshot IDとcontent hash

stateがworkflowの正本になるため、schema変更はmigration問題になる。短命prototypeと長期運用を同じstate設計で始めない。

永続化とthread

Checkpointerは各superstepのstateを保存し、thread IDで連続実行を識別する。processが終了しても同じthreadから再開できる。

  • 入力とconfigからthreadを一意に決める。
  • checkpointer backendのdurabilityをSLAへ合わせる。
  • stateへ秘密情報を直接保存しない。
  • schema versionをstateへ含める。
  • 古いcheckpointを再利用できる条件を定める。

checkpointがあるだけでexactly-onceになるわけではない。外部APIや送信toolはidempotency keyを持つ必要がある。

中断と人間承認

interrupt()でnodeを停止し、承認UIへpayloadを返せる。再開時はCommandで人間の判断を注入する。

TypeScript
import { interrupt, Command } from "@langchain/langgraph";

async function approvalNode(state: State) {
  const decision = interrupt({
    kind: "publish-approval",
    summary: state.draft,
  });
  return { approved: decision === "approve" };
}

await graph.invoke(new Command({ resume: "approve" }), {
  configurable: { thread_id: "thread-42" },
});

承認対象には内容だけでなく、hash、対象resource、実行予定tool、費用、期限を含める。再開前に対象が変わっていないことを検証する。

Durable execution

長時間workflowでは「nodeが成功した後、checkpoint前にprocessが落ちる」境界が重要になる。副作用nodeは再実行される可能性を前提に設計する。

副作用必要な対策
メール送信message IDによるidempotency
決済provider idempotency keyと状態照合
ファイル公開staging、atomic rename、content hash
外部job起動job IDを先に確保し再照会
DB更新transactionまたはcompare-and-swap
Checkpoint ≠ exactly once

LangGraphはstate再開を提供する。外部世界の副作用の一意性はapplicationが保証する。

Subgraphと境界

大きなworkflowはsubgraphへ分割できる。分割単位は組織の役職ではなく、state contractと再開境界で決める。

  • 入力・出力schemaが独立している。
  • 内部stateを外へ漏らさない。
  • 再実行policyがまとまっている。
  • 別チームまたは別versionで管理できる。

単一agentをsubgraphとして包む場合、Pi SDKやLangChain agentをnode内で呼べる。このときgraphがworkflow stateを所有し、agent sessionは一nodeの一時状態に留める。

失敗設計

失敗扱い
model rate limitnode retry policyまたは明示attempt
tool validationcontent errorとしてbranch
credential missingretryせずblocked
human timeout期限切れbranch
stale approvalhash mismatchで再承認
unknown external dispatch自動再送せず照合待ち

例外をすべてretryへ流すと二重副作用が起きる。failure vocabularyをstateとtraceへ残す。
