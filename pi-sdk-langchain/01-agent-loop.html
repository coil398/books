エージェントループとは何か

エージェントは「賢いチャット」ではない。実装上は、モデル出力を検査し、tool callがあれば実行し、その結果をmessagesへ追加して再びモデルを呼ぶ反復処理である。モデルは意思決定器、ホストプログラムは実行器である。

Agent = Model policy + State + Tool executor + Stop rule

長期記憶、並列実行、承認、再開、予算管理、sandboxはこの定義に自動では含まれない。必要なら別層で実装する。

状態の最小構成

状態意味壊れたときの症状
systemPrompt役割、制約、tool利用規則コーディング用指示が文章処理へ混入する
messages会話履歴とtool result古い指示、別runの混線
model実際に呼ぶprovider/modelaliasやsilent fallbackで再現不能
toolsモデルへ公開する能力権限過大、未宣言操作
stop state完了、失敗、cancel、上限無限反復、途中成功の誤採用
usagetoken、request、費用費用異常を検知不能

一回の反復

  1. stateからprovider requestを作る。
  2. モデルへ送信しresponseを受ける。
  3. assistant messageをstateへ追加する。
  4. tool callがなければ停止判定へ進む。
  5. tool callがあればschemaと権限を検証する。
  6. toolを実行しresultをmessagesへ追加する。
  7. 予算、反復数、cancelを確認して次のcallへ進む。

最も危険なのはモデルの自然文を「実行済みの事実」と誤認することである。「保存しました」と書いても、write toolの成功記録がなければ保存していない。自然文ではなくtool eventとartifactを正本にする。

ツール契約

toolは関数ではなく、name、description、input schema、権限、timeout、idempotency、result schemaの集合である。安全な設計ではモデルにpathやURLを自由入力させず、artifactIdのような論理IDを受け、ホスト側が実体へ解決する。

TYPESCRIPT
type Tool<I, O> = {
  name: string;
  description: string;
  inputSchema: Schema<I>;
  execute(input: I, signal: AbortSignal): Promise<O>;
};

const writeReport: Tool<
  { reportId: string; content: string },
  { contentHash: string }
> = {
  name: "write_report",
  description: "Write one declared report by reportId.",
  inputSchema: ReportWriteSchema,
  async execute(input, signal) {
    assertDeclaredReport(input.reportId);
    signal.throwIfAborted();
    return atomicWrite(input);
  },
};

システムプロンプトと既定値

「独自system promptを指定できる」と「最終system promptを完全に支配できる」は違う。frameworkがtool説明、安全規則、context file、memory、middleware instructionを追加する場合、モデルが受け取る内容は入力した一文より広い。

  • 既定promptを置換するのか、追加するのか。
  • project/homeのinstruction fileを自動読込するか。
  • structured output用toolやschema説明が注入されるか。
  • summarization middlewareが履歴を書き換えるか。
検査対象は設定値ではない

モデル送信直前の最終request、またはsessionが持つ最終system promptとtool一覧を検査する。

停止条件

条件用途判定主体
tool callなし通常chatの終了loop
submit tool成功構造化成果物の確定custom tool
最大反復数暴走防止runtime
token/cost上限予算防止runtime
deadlineSLAhost process
全artifact検証成功業務完了application
human approval高リスク操作orchestrator

業務agentでは専用submit toolを用意し、required outputが揃った場合だけ成功させる。自然文最終回答は説明であり、機械的完了証拠ではない。

再試行とフォールバック

再試行は同一契約の再実行、fallbackは別model/providerなど別契約への切替である。

動作例影響
transport retry接続切断前に同一requestを再送idempotencyが必要
agent retry新attemptとして再実行入力pinとattempt IDが必要
model fallbackmodel AからBへ変更品質・費用・傾向が変わる
provider fallback公式APIからproxyへ変更認証・保存・実装差が変わる
output repairschema違反を追加promptで修正追加callと履歴変形

便利な自動復旧は厳密なsystemでは隠れた非決定性になる。必要なら上位層が別attemptとして管理する。

構造化出力

  1. provider native schema
  2. 最終結果専用tool
  3. 自然文JSONをparse

信頼性は通常この順で高い。LangChainはprovider strategyとtool strategyを抽象化する。Pi SDKではcustom submit toolまたはprovider機能を明示的に組む。

権限と監査

安全性はモデルの人格ではなくtool boundaryで決まる。読み取り専用agentへwrite toolを渡さない。network不要ならHTTP toolを登録しない。shell不要ならbashを無効化する。

  • tool allowlistはresourceまで狭める。
  • credentialをpromptやtool resultへ返さない。
  • tool call/resultをappend-only eventとして記録する。
  • model/provider/thinkingをprovenanceへ残す。
  • 失敗時に部分成果物を公開しない。
  • cancel後の遅延完了を採用しない。

最小実装

TYPESCRIPT
async function runAgent(state: AgentState): Promise<AgentResult> {
  for (let turn = 0; turn < state.maxTurns; turn++) {
    state.signal.throwIfAborted();
    const response = await state.model.generate({
      system: state.systemPrompt,
      messages: state.messages,
      tools: state.tools.map(toModelTool),
      signal: state.signal,
    });
    state.messages.push(response.message);
    if (response.toolCalls.length === 0) {
      return validateFinalResponse(response.message);
    }
    for (const call of response.toolCalls) {
      const tool = state.toolRegistry.get(call.name);
      if (!tool) throw new Error(`Unknown tool: ${call.name}`);
      const input = tool.inputSchema.parse(call.arguments);
      const output = await tool.execute(input, state.signal);
      state.messages.push({
        role: "tool",
        toolCallId: call.id,
        content: JSON.stringify(output),
      });
    }
  }
  throw new Error("MAX_TURNS_EXCEEDED");
}

Pi SDKもLangChainも、この骨格へprovider差、events、session、middlewareなどを追加したものと理解すると比較しやすい。

理解度チェック

モデル自然文を実行証拠にしない理由は何か。
モデルはtool実行状態を保証しないため。tool event、result、artifact hashを証拠にする。
再試行とfallbackの違いは何か。
再試行は同一契約の再実行。fallbackはmodel/providerなど契約自体の変更。
業務成果物の完了判定に有効な設計は何か。
required outputを検証する専用submit toolを用意する。
