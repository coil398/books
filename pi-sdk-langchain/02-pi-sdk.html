Pi SDKの位置づけ

Piは単なるターミナルUIではない。モノレポにはprovider差を吸収するLLM API、model-tool反復を持つagent core、coding agent、TUI、Web UIが分離されている。Pi SDKはcoding-agent packageの機能をNodeアプリへ埋め込む入口である。

中心にあるのは巨大なworkflowではなく、一つのsessionでmodel、prompt、messages、tools、thinking level、イベントをどう管理するかである。subagent、plan mode、永続workflowを標準の正解として固定しない。必要な能力はextensionまたは上位アプリが追加する。

Piの「minimal」の意味

機能が乏しいのではない。中核のagent loopを小さく保ち、周辺方針を利用者へ返している。

パッケージ群

パッケージ責務利用場面
pi-aiprovider統一、stream、tool call、usage最小のmodel接続だけ欲しい
pi-agent-coremessages、tool loop、events独自agent runtimeを作る
pi-coding-agentsession、resource、tools、CLI/SDK実用的なharnessを埋め込む
pi-tuiterminal UI部品対話CLI
pi-web-uibrowser UIWeb front end

Pi SDKという呼び方は通常coding-agentのSDKを指す。さらに薄い境界が必要ならagent-coreへ降りられる。この段階選択がPiの重要な特徴である。

既定値は空ではない

Piは薄いが、何も指定しない実行は空白ではない。coding agentとして便利に使えるよう、model解決、標準tools、context files、skills、extensions、session保存などの既定動作がある。

項目無指定時厳格worker
modelsettingsまたは利用可能modelから解決provider/modelを完全指定
system promptcoding agent向け構成最終promptを置換・検査
toolsread/write/edit/bash等独自toolだけへ置換
contextAGENTS.md等を探索空cwd・専用loader
session永続保存可能runごとのin-memory
extensions標準探索可能version pinしたものだけ
「変なシステムプロンプトがない」は誤り

正しい評価は、SDKなら最終system promptとtool集合を明示的に支配し、runtime stateから検査できる、である。

SDKで制御する

TypeScript
import {
  createAgentSession,
  SessionManager,
  SettingsManager,
} from "@earendil-works/pi-coding-agent";

const model = registry.getModel("provider", "exact-model-id");
if (!model) throw new Error("MODEL_UNAVAILABLE");

const { session } = await createAgentSession({
  model,
  thinkingLevel: "high",
  customTools: [readInput, writeOutput, submitResult],
  sessionManager: SessionManager.inMemory(),
  settingsManager: SettingsManager.inMemory({
    retry: { enabled: false },
    compaction: { enabled: false },
  }),
  resourceLoader: emptyResourceLoader,
});

assert.equal(session.agent.state.model.id, "exact-model-id");
assert.deepEqual(
  session.agent.state.tools.map(t => t.name).sort(),
  ["read_input", "submit_result", "write_output"],
);
await session.prompt(task);
await session.agent.waitForIdle();

重要なのは設定オブジェクトだけでなく、生成後のresolved stateを検査できる点である。model alias、ambient extension、余計なtoolが混入していれば実行前に止められる。

Resource Loader

Resource Loaderはcontext files、skills、prompt templates、extensions、themesを供給する。人間が使うCLIでは生産性を上げるが、自動workerでは再現性を壊す可能性がある。

  • homeの指示ファイルが特定端末だけに存在する。
  • project extensionがtoolを追加する。
  • skill更新で同じtaskの挙動が変わる。
  • packageが任意コードを実行する。

対話CLIは探索を許し、production workerは空loaderから始める。両方を同じ設定にしない方がよい。

ツール境界

Pi SDKではmodelへ見せるtool配列を直接制御できる。promptで「bashを使うな」と頼むのではなく、bash schema自体を渡さない。

TypeScript
session.agent.state.tools = [
  tool("read_input", ReadSchema, readDeclaredInput),
  tool("write_output", WriteSchema, atomicWriteOutput),
  tool("submit_result", SubmitSchema, validateAndSubmit),
];

for (const tool of session.agent.state.tools) {
  assert(ALLOWED_TOOLS.has(tool.name));
}

ただしtool implementationは同一processの権限を持つ。PiがOS sandbox、path boundary、credential maskingを自動で保証するわけではない。必要なら専用worker processへ隔離する。

Sessionとイベント

AgentSessionはmessages、model、thinking、tools、streaming stateを持つ。購読可能なイベントから、message delta、tool開始、tool終了、errorを監査ログへ流せる。

TypeScript
const unsubscribe = session.subscribe(event => {
  if (event.type === "tool_execution_start") auditStart(event);
  if (event.type === "tool_execution_end") auditEnd(event);
  if (event.type === "message_update") recordDelta(event);
});
try {
  await session.prompt(task);
  await session.agent.waitForIdle();
} finally {
  unsubscribe();
}

業務workflowの正本をPi sessionにする必要はない。上位stateとartifactから新しいsessionを再構築する方が、再開境界と入力pinを明確にできる。

ExtensionsとPackages

Extensionはtool、command、event interception、provider、UI、compactionを追加できる。Packageはextensions、skills、prompts、themesをnpmまたはGitで配布する単位である。

これは強力だが、Packageは単なるprompt集ではない。任意コードを含み得る。導入時はsource review、exact version pin、権限分離が必要になる。

非コーディング化

非コーディングagentへ変える本質はrole文の変更ではない。coding toolsとfilesystem探索を捨て、業務の論理toolだけを公開することである。

用途公開tool閉じる能力
文書レビューread_document、record_issue、submit_reviewshell、任意write
調査レポートsearch_source、read_source、write_section、submitfilesystem全体
問い合わせ分類read_ticket、assign_label、submit外部送信
データ品質診断read_profile、record_finding、submit任意SQL

評価

強い点
  • 単一sessionを直接扱える
  • 最終model/prompt/toolsを検査可能
  • CLI・RPC・SDKを選べる
  • workflow engineを強制しない
弱い点
  • durable workflowは別実装
  • 組織向けobservabilityは別途
  • extension審査が必要
  • sandboxは自動ではない
適する設計
  • 既存アプリへのloop埋込
  • tool境界が厳密
  • 独自state/artifact契約
  • 薄い依存を重視

理解度チェック

Piがminimalでも無指定実行が空でない理由は何か。
coding tools、resource discovery、model/session解決などの既定値を持つため。
非コーディング化で最初に変えるべきものは何か。
promptより先にtool集合とresource loaderを業務境界へ置き換える。
Packageをsource reviewすべき理由は何か。
任意コードを実行するextensionを含められるため。
