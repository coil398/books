なぜ比較が混乱するのか

Pi SDKとLangChainは、どちらもモデルを呼び、ツールを渡し、エージェントを動かせる。そのため「同じ製品の軽量版と重量版」に見える。実際には設計の中心が違う。

Pi SDKの中心は、一つのエージェントセッションをどう実行するかである。モデル、システムプロンプト、ツール、メッセージ履歴、thinking level、イベントを一つの実行単位として扱う。LangChainの中心は、LLMアプリケーションを構成する共通部品と既製のエージェント構造である。モデル統合、ツール、構造化出力、middleware、LangGraphとの接続を同じ流儀で組み合わせる。

LangGraphまで含めると比較軸はさらに増える。LangGraphは単なる「LangChainの高度版」ではなく、状態グラフと長時間実行を扱うオーケストレーションランタイムである。

最初に捨てる問い

「どちらが上か」ではなく、「不足している層はどこか」を先に決める。単一エージェント実行ならPi SDK、広いLLMアプリ部品ならLangChain、永続的な状態遷移ならLangGraphである。

四つの層で分ける

層主な責務代表的な失敗
モデル接続層provider API、stream、tool-call形式、認証、usageprovider差異が上位へ漏れる、モデルIDが曖昧になる
エージェントループ層prompt、messages、tools、tool結果の再投入、停止、abort無限ループ、余計なツール、暗黙の既定値
オーケストレーション層複数step、分岐、並列、再開、承認、長時間状態二重実行、stale state、途中成果物の混線
運用層観測、評価、権限、課金、deploy、監査、version pin再現不能、費用急増、秘密情報流出

モデル接続層

「OpenAI互換だから同じ」ではない。tool call ID、assistant reasoningの保持、stream event、structured output、cache、最大出力、エラー分類がproviderごとに異なる。Piでは統一LLM APIが独立しており、LangChainではprovider integrationが共通ChatModelへ接続される。

エージェントループ層

モデルへ一度質問して終わる処理と、モデルがツールを選び、その結果を受けて次の判断をする処理は別物である。後者にはmessages更新、tool実行、abort、最大反復、最終出力判定が必要になる。Pi SDKが最も直接扱うのはこの層である。LangChainのcreateAgent()もこの層を提供するが、内部はLangGraphのグラフとして構築される。

オーケストレーション層

「調査して、評価して、承認されたら配信する」のような複数工程を一つの巨大agentへ任せると境界が消える。工程ごとの入力、出力、再試行、承認、再開を明示するのがオーケストレーションである。LangGraphの中心はここにある。

運用層

実運用では、最終回答の質より先に「どのモデルが動いたか」「何回APIを呼んだか」「どのツールが実行されたか」「途中で落ちたらどこから再開するか」が問題になる。Piはイベント購読を提供する。LangChain/LangGraphはLangSmithとの統合を持つ。

三者の正体

Pi SDK

薄く具体的なagent実行ハーネス。session、model、tools、eventsを直接握る。

LangChain

LLMアプリの共通部品と高水準agent API。provider統合、middleware、structured outputが強い。

LangGraph

状態グラフと長時間実行のruntime。分岐、永続化、中断、再開、人間承認を管理する。

Pi SDKとLangChainは単一agent loopの範囲で競合する。LangChainは周辺抽象化が広く、Pi SDKは実行面が薄い。LangGraphは比較対象であると同時に、LangChain agentの実行基盤でもある。

実務上の結論

単一agentを自分の契約で厳密に動かすならPi SDK。providerやtool統合を短期間で揃えるならLangChain。長時間・複数工程・承認・再開を要件に持つならLangGraph。
