# 形式手法とテスト技法の地図

この章では Lean、TLA+、Property-Based Testing（PBT）が何を保証し、何を保証しないかを比較する。
前提は、型付き言語で小さなプログラムを書いた経験と、ユニットテストの読解である。
証明支援系やモデル検査の数学を先に覚える必要はない。

## 1. まず「保証」を分解する

「バグがない」という一文は大きすぎる。
実務では、対象、前提、入力範囲、時間範囲を決めてから保証を語る。

| 技術 | 主な対象 | 探索・証明の範囲 | 得られる主な保証 | 主なコスト |
| --- | --- | --- | --- | --- |
| Lean | 関数、データ構造、数学的定理 | 形式化した全入力 | 定理が前提から導けること | モデル化と証明の初期費用 |
| TLA+ / TLC | 分散・並行システムの状態遷移 | 有限に切った状態空間 | 不変条件違反がないこと、反例 | 状態爆発、抽象化の難しさ |
| PBT | 実装と実行可能な性質 | 生成した有限個の実行 | 反例が見つからなかったこと | ジェネレータ設計、確率的カバレッジ |

Lean は「この定理はすべての自然数について成立する」を証明する。
TLC は「この有限サイズのモデルで、到達可能な状態に違反がない」を網羅する。
PBT は「この実装に対し、生成した入力群で性質が壊れなかった」を確認する。

この違いを混同すると、100 万ケースのテストを「証明」と呼んだり、形式仕様を一度書いたので本番コードも正しいと思ったりする。

## 2. バグを見つけることと、ないことを証明すること

例として、注文金額を計算する関数を考える。

```python
def total(prices: list[int], tax: int) -> int:
    return sum(prices) + tax
```

通常の例示テストは代表値を固定する。

```python
def test_total():
    assert total([100, 200], 30) == 330
```

これは入力 `[100, 200]` にバグがないことを示す。
空リスト、負数、オーバーフロー、税率の解釈は別問題である。

PBT は入力を広げる。

```python
from hypothesis import given, strategies as st

@given(st.lists(st.integers(min_value=0), max_size=20),
       st.integers(min_value=0))
def test_total_agrees_with_reference(xs, tax):
    assert total(xs, tax) == sum(xs) + tax
```

ここで反例を見つければ、PBT はバグ発見器として強い。
しかし生成戦略にない入力や、未記述の性質については沈黙する。

Lean では同じ関係を論理式にして、証明項を作る。

```lean
import Mathlib

def total (prices : List Nat) (tax : Nat) : Nat := prices.sum + tax

theorem total_spec (prices : List Nat) (tax : Nat) :
    total prices tax = prices.sum + tax := by
  rfl
```

この証明は関数定義の展開に過ぎないが、すべての `prices` と `tax` に対して成立する。
一方、`total` の実装が外部 DB の値、時計、ネットワーク、整数幅に依存するなら、その依存も形式化しなければならない。

## 3. 三つの技術の境界

### Lean が得意なもの

Lean は純粋関数、データ構造、アルゴリズムの正しさに向く。
型で不変条件を表すと、呼び出し側が不正な状態を作れない設計もできる。

```lean
structure NonEmptyPage where
  items : List α
  nonempty : items ≠ []

def first (p : NonEmptyPage) : α :=
  match p.items, p.nonempty with
  | x :: _, _ => x
  | [], h => (h rfl).elim
```

ただし、データベースの分散実行やスケジューラの全 interleaving を Lean が自動で調べるわけではない。
そのためのモデル化と証明を人が用意する必要がある。

### TLA+ が得意なもの

TLA+ は状態変数とアクションを直接表す。
「在庫が負にならない」「二つのクライアントが同じロックを持たない」のようなシステム性質が読みやすい。

```tla
VARIABLES stock, bought

Init == /\\ stock = 2 /\\ bought = {}
Buy(u) == /\\ u \\notin bought /\\ stock > 0
           /\\ stock' = stock - 1 /\\ bought' = bought \\cup {u}
Next == \\E u \\in Users : Buy(u)
Inv == stock >= 0 /\\ Cardinality(bought) <= 2
```

TLC は有限の `Users` と `stock` を列挙して反例を出す。
無限個のユーザーや実際のネットワーク遅延をそのまま検証するものではない。

### PBT が得意なもの

PBT は実装そのものを動かすため、パーサ、API、シリアライザ、状態機械の接続不備に強い。
縮小された再現例が得られるので、例示テストよりデバッグしやすい場合がある。

```typescript
import fc from "fast-check";

fc.assert(fc.property(fc.array(fc.integer()), xs => {
  const sorted = [...xs].sort((a, b) => a - b);
  return sorted.length === xs.length &&
    sorted.every((x, i) => i === 0 || sorted[i - 1] <= x);
}));
```

PBT は「仕様のないランダムテスト」ではない。
重要なのは入力生成器より先に性質を決めることである。

## 4. コスト対効果

| 観点 | Lean | TLA+ | PBT |
| --- | ---: | ---: | ---: |
| 最初の一例まで | 高 | 中 | 低 |
| 深い仕様バグへの強さ | 高 | 高 | 中 |
| 実装との距離 | 型・定義による | 抽象モデル | 実装そのもの |
| 反例の読みやすさ | 証明失敗の位置 | 状態トレース | 縮小入力と実行 |
| 無限範囲の保証 | 得意 | 抽象化次第 | 苦手 |
| 並行性の探索 | 手動設計が必要 | 得意 | 工夫が必要 |
| CI への導入 | ビルド時 | 小モデル | 容易 |

費用はツールの実行時間だけではない。
最も大きい費用は、何を保証したいかを明文化する時間である。
この費用は無駄ではなく、設計の曖昧さを早期に露出させる。

## 5. いつ何を選ぶか

| 状況 | 第一候補 | 理由 | 補助 |
| --- | --- | --- | --- |
| 純粋な計算ロジック | Lean | 全入力を扱える | PBT |
| 分散ロック、注文、再試行 | TLA+ | 順序と同時実行を列挙できる | PBT |
| JSON、パーサ、SDK | PBT | 実装境界を大量に動かせる | Lean |
| 高リスクな決済中核 | TLA+ + Lean | プロトコルと計算を分離して保証 | PBT |
| 仕様がまだ曖昧 | PBT の例示から開始 | 期待動作を発見できる | TLA+ |

選択に迷ったら、まず失敗モードを一文で書く。
「二重購入が起きる」なら TLA+、「丸めが一円ずれる」なら Lean または PBT、「未知の JSON で落ちる」なら PBT が入口になる。

## 6. 現実的な導入順序

1. 既存の重要な不変条件を文章にする。
2. PBT で実装境界に反例を集める。
3. 並行性や再試行があるなら、最小の TLA+ モデルを作る。
4. 数式の中心部分を Lean の純粋関数として切り出す。
5. 形式仕様、証明、テストを CI の別ジョブにする。

この順序は絶対ではない。
チームが TLA+ に慣れているなら先にモデルを書いてよい。
重要なのは、ツール導入を目的にせず、失敗すると高価な性質から始めることである。

## 7. 縦切りの例

在庫二つの商品を二人が購入するケースを考える。

```tla
CONSTANT Users
VARIABLE stock, orders

Init == /\\ stock = 2 /\\ orders = {}
Purchase(u) == /\\ u \\notin DOMAIN orders
                /\\ stock > 0
                /\\ orders' = [orders EXCEPT ![u] = "paid"]
                /\\ stock' = stock - 1
Next == \\E u \\in Users : Purchase(u)
Spec == Init /\\ [][Next]_<<stock, orders>>
```

ここで `stock >= 0` と `Cardinality(orders) <= initialStock` を TLC で検査する。
同じ購入関数を PBT で並行イベント列に対して実行する。
残額計算や注文金額の整合性は Lean で証明する。

三つは重複ではなく、異なる層の穴を埋める。

## 8. 形式化の粒度

すべてを形式化しようとすると失速する。
次の表で対象を切る。

| 層 | 形式化する候補 | テストへ残す候補 |
| --- | --- | --- |
| 業務不変条件 | 在庫非負、権限、金額 | 文言、UI の見た目 |
| 状態遷移 | 支払い、返金、失効 | 外部サービスの実応答 |
| 数値計算 | 税、割引、丸め | DB ドライバ |
| API 契約 | 型、必須条件 | ブラウザ互換性 |
| 性能 | ほぼ扱わない | 負荷、レイテンシ |

形式化しないものは、無視するのではなく、テスト・監視・運用手順に置く。

## 9. よくある誤解

### 「TLC が通ったので本番も安全」

モデルの抽象化が本番と一致する範囲でのみ安全である。
キューを集合にしたなら、重複、順序、再配信を落としている可能性がある。

### 「Lean の定理があるので実装も同じ」

証明した関数が本番コードと同じ定義であることが必要である。
別言語への手書き移植は refinement の穴になる。

### 「PBT のケース数を増やせば証明に近づく」

ケース数は確率を上げるが、未生成の領域を消さない。
性質、生成器、縮小器の品質がケース数より重要なことが多い。

## 12. 最小の意思決定テンプレート

```text
対象:
失敗すると起きること:
保証したい性質:
前提条件:
有限モデルにできるか:
純粋計算に切り出せるか:
実装を大量に動かせるか:
第一候補:
反例を誰が直すか:
```

テンプレートの空欄が埋まらないとき、ツール選定を先送りする。
形式手法は曖昧な要求を魔法のように正しくしてくれない。
ただし、空欄を埋める過程で曖昧さを可視化する効果は大きい。

## 14. 保証の書式

保証は次の四つ組で記録する。

```text
対象 = 何の状態・関数を対象にするか
前提 = 入力、環境、モデルの制約は何か
性質 = 何が常に、またはいつか成立するか
証拠 = 定理、モデル検査結果、テスト実行結果のどれか
```

| 悪い記述 | 良い記述 |
| --- | --- |
| 購入は安全 | 在庫 1、利用者 2 のモデルで stock >= 0 |
| 金額は正しい | 非負の明細で小計の append が加法に一致 |
| API は壊れない | 制約内の JSON で decode(encode(x)) = x |
| ロックは公平 | 有効な待ちプロセスに弱公平性を仮定 |

前提を記録しない証拠は、再利用できない。
モデルの定数を変更したら、証拠の範囲も変更履歴に残す。

## 15. 失敗モードから逆算する

```text
二重請求       -> 同一キーの冪等性 -> TLA+ + PBT
負の在庫       -> 保存不変量       -> TLA+ + Lean
丸め誤差       -> 数値契約         -> Lean + PBT
未知の入力     -> パーサ契約       -> PBT
失効後の利用   -> 状態遷移         -> TLA+ + PBT
無限待ち       -> 進行性           -> TLA+ liveness
```

同じ障害を三つの技術で重複して書く必要はない。
ただし、層をまたぐ性質は接続テストで確認する。

## 16. レビューで使う質問

| 質問 | 目的 |
| --- | --- |
| どの値域を保証するか | 網羅範囲を固定する |
| 何が atomic か | 競合の粒度を固定する |
| 失敗時の状態は何か | retry と rollback を漏らさない |
| 時計は誰が進めるか | liveness と期限を検査する |
| 反例は最小か | 修正を読める形にする |
| 外部依存は何か | 形式化とテストの境界を明確にする |

## 17. 最小の導入計画

```text
第1週: 過去障害を三つ選び、性質を文章化
第2週: PBT で入力境界を固定
第3週: TLA+ で二人・容量一の競合を検査
第4週: 金額または権限の純粋関数を Lean 化
毎週: 反例を回帰テストと設計文書へ移す
```

導入の成否は、証明数ではなく、変更時に不変条件が参照されるかで測る。

## 18. 学習の進め方

Lean は `example` を一つずつ `#check` で確認する。
TLA+ は最小定数で反例を読む。
PBT は一つの性質に一つの generator から始める。
三つとも、長い教材を読むだけでなく、意図的に一行壊して反例を見ると定着する。

```text
定義を読む -> 性質を一文にする -> 最小コードを書く
-> 正常系を確認 -> 一行壊す -> 反例を説明する
```

## 19. 章の最終チェック

- [ ] 「見つけた」のか「証明した」のかを区別した
- [ ] Lean の定理に前提を明記した
- [ ] TLC の定数と仕様を保存した
- [ ] PBT の shrink 済み例を保存した
- [ ] 形式化しない外部要素をテスト計画に書いた
- [ ] 反例を修正する責任者を決めた
- [ ] CI で証拠を再生成できる
- [ ] 章間の境界をチームが説明できる

以上が三手法を使うための最低限の地図である。

## 20. 用語の対応

| 用語 | この教材での意味 |
| --- | --- |
| 仕様 | 実装に先立つ振る舞いの記述 |
| 前提 | 性質が成立するために仮定する条件 |
| 不変条件 | 遷移しても保持する述語 |
| 反例 | 性質を破る入力または状態列 |
| refine | 抽象仕様を具体実装へ対応づけること |
| oracle | 期待値を判定する独立の基準 |

用語を揃えるだけでも、設計レビューの議論は短くなる。
証拠の名前と範囲をチケットに残す。

## 21. 最後の判断

迷ったら、最も高価な失敗を一つ選び、その失敗を最小の例にする。
最小例が状態の順序なら TLA+、計算式なら Lean、実装境界なら PBT から始める。
必要になったら他の技術を追加する。

## 22. 記録の粒度

証拠にはツールの版、対象コミット、入力範囲、実行日時を添える。
これは証明を弱めるためではなく、再現性を確保するためである。
過去の反例と現在の仕様を比較できれば、技術導入の効果も説明できる。

## 23. 証拠の保存

```text
toolchain: 固定する
model constants: 保存する
seed: 記録する
counterexample: fixture にする
owner: 決める
```

形式手法もテストも、実行結果を再利用できて初めてチームの知識になる。
CI の成功バッジだけでは、何を検査したか分からない。

## 24. 章の使い方

概要から入り、対象の章のコードを一つ実行し、最後に統合章の表へ戻る。
読む順序より、反例を一つ説明できることを優先する。

## 25. 境界の再確認

保証範囲の外側には、監視、ログ、レビュー、運用手順を置く。
形式手法は品質活動全体の代替ではなく、重要な不変条件を強くする部品である。

導入後も保証範囲を定期的に見直す。

## 13. まとめ

Lean は定義と証明の整合性を保証する。
TLA+ は有限モデルにおける状態遷移の反例を探す。
PBT は実装を多様な入力と操作列で揺さぶる。
実務では一つを信仰せず、失敗モードに合わせて層を分ける。
次章から、すべての例を実行可能な小さな形へ落とし込む。
