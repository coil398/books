Chapter 05 · 形式手法とテスト技法

Property-Based Testing の基礎

性質・ジェネレータ・shrink・失敗運用を一つのテスト設計として学びます。

対象PythonまたはTypeScriptのテスト経験者
成果物再現可能なproperty testを設計できる
読む目安60〜90分

この章で学ぶこと

  • 例示テストを一般性へ広げる
  • 現実の制約をgeneratorへ入れる
  • 状態機械・seed・CIを運用する

前提知識

  • Python/TypeScriptの基本
  • assertとテストランナー
  • データ構造と状態更新

所要時間の目安

往復性を一つ書き、generatorと縮小反例の流れを確認します。

PBTを実行できる最小環境

Property-Based Testing（PBT）は、入力の多様性を増やすだけの乱数テストではありません。性質・ジェネレータ・shrink・失敗運用を組み合わせ、実装が契約を破る最小例を見つける設計技法です。

Shell / Python
python -m venv .venv
. .venv/bin/activate
python -m pip install hypothesis pytest
pytest -q
Python
# test_strings.py
from hypothesis import given, strategies as st

@given(st.text())
def test_identity(s: str) -> None:
    assert s == "".join(list(s))
Shell / TypeScript
npm init -y
npm install --save-dev typescript tsx fast-check vitest
npx vitest run
TypeScript
import fc from "fast-check";
import { test } from "vitest";

test("reverse is involutive", () => {
  fc.assert(fc.property(fc.array(fc.integer()), xs => {
    return [...xs].reverse().reverse().every((x, i) => x === xs[i]);
  }));
});

PBTの考え方は言語に依存しません。たとえばHaskellでも、純粋関数を実行可能な性質の対象にできます。

Haskell
module Main where

double :: Integer -> Integer
double n = n + n

main :: IO ()
main = print (double 21)
外部サービスを生成ケースごとに呼ばない

PBTはfake clock、fake payment、ローカルDBなど観測可能な依存を注入します。実ネットワークを全ケースから叩くと、遅さ・料金・flaky失敗が仕様の反例と混ざります。

例示テストから性質へ

Python
def reverse(xs: list[int]) -> list[int]:
    return list(reversed(xs))

def test_reverse_example():
    assert reverse([1, 2, 3]) == [3, 2, 1]

例示テストは具体的な入出力を伝える良い文書です。しかし、順序を変えた場合、空リスト、重複、長大な入力については別のケースが必要です。PBTでは、例の背後にある一般性を言語化します。

Python / Hypothesis
from hypothesis import given, strategies as st

@given(st.lists(st.integers()))
def test_reverse_involution(xs: list[int]):
    assert reverse(reverse(xs)) == xs

保証したいのは往復性です。破れると編集画面のUndoやデータ変換が壊れます。PBTが見ているのは、generatorが生成したリストの範囲と、ここで書いた性質だけです。

例示テストPBT共通の注意
固定入力を説明する入力の族を生成する契約を明文化する
失敗値が直接見えるshrink後の最小値が見える失敗を回帰資産にする
少数で速いgenerator次第で広い例数は証明ではない
仕様の具体例に強い不変・往復・単調性に強い外部依存を観測可能にする

性質の見つけ方

パターン数式・関係典型例破れると
往復decode(encode(x)) = xJSON・セーブ再読込で値が変わる
不変操作後も条件が残る在庫・盤面負数・重複・破損
冪等f(f(x)) = f(x)PUT・失効再送で二重効果
可換f(a,b) = f(b,a)集合和順序の意図を誤る
単調性入力を増やして悪化しない権限・スコアバランスの逆転
モデル比較実装状態 = 簡単なモデル状態認可・状態機械接続分岐の抜け
メタモルフィック入力変換に応じ出力変換ソート・単位変換変換規則の崩れ

性質が一文で書けないなら、対象の仕様がまだ曖昧です。期待値を大量に作る前に、観測したい関係を名前付きテストとして固定します。

Python
from hypothesis import given, strategies as st

@given(st.lists(st.integers()))
def test_sort_is_idempotent(xs: list[int]):
    assert sorted(sorted(xs)) == sorted(xs)

@given(st.sets(st.integers()), st.sets(st.integers()))
def test_union_is_commutative(a: set[int], b: set[int]):
    assert a | b == b | a

ジェネレータを契約として設計する

ジェネレータは、現実の入力制約をテストの構造へ落とします。広すぎると無効入力ばかりになり、狭すぎるとバグの領域を作りません。ドメインの制約とAPIのエラー契約を分けて生成します。

Python / Hypothesis
from hypothesis import strategies as st

user_ids = st.text(
    alphabet=st.characters(whitelist_categories=("Ll",)),
    min_size=1,
    max_size=12,
)
prices = st.integers(min_value=0, max_value=1_000_000)
orders = st.fixed_dictionaries({
    "user": user_ids,
    "price": prices,
    "items": st.lists(
        st.integers(min_value=1, max_value=99),
        max_size=20,
    ),
})
入力strategy意識する境界
IDtext空・長大・Unicode
金額integers0・最大・負数
配列lists空・一要素・大量
JSONrecursive / fixed_dictionaries深さ・欠落・未知キー
操作列lists of commands空・同一操作・長列
Python / boundary strategy
from hypothesis import strategies as st

small_amount = st.one_of(
    st.just(0),
    st.just(1),
    st.just(100),
    st.just(101),
    st.integers(min_value=0, max_value=1_000_000),
)

境界値を手書きの例示テストだけにせず、strategyの中に置くと、一般性と境界の意図が同じ場所に残ります。invalid入力を作る場合は、返すHTTPエラーや例外型も性質にします。

assumeを濫用しない

Python / bad example
from hypothesis import given, assume, strategies as st

@given(st.integers(), st.integers())
def test_division_round_trip(a: int, b: int):
    assume(b != 0)
    assert (a / b) * b == a

この性質は浮動小数では一般に偽です。さらに`assume`を大量に使うと、生成した入力を捨てるため実行効率が落ち、仕様の穴を隠します。

Python / structured input
from hypothesis import given, strategies as st

nonzero = st.integers().filter(lambda value: value != 0)

@given(st.integers(), nonzero)
def test_integer_division_has_remainder(a: int, b: int):
    quotient, remainder = divmod(a, b)
    assert a == quotient * b + remainder
除外ではなく構造化

依存する値は`@st.composite`で一緒に生成し、無効状態を作りにくいデータ型へ移します。どうしても除外する場合は、除外率をCIで監視します。

shrinkで最小反例を読む

shrinkは、失敗を維持しながら入力を短く・小さく・単純にします。巨大な業務JSONではなく、二要素のリストや一つの操作へ縮むと、原因を説明しやすくなります。

Python / Hypothesis
from hypothesis import given, strategies as st

@given(st.lists(st.integers(), min_size=1))
def test_no_negative(xs: list[int]):
    assert all(x >= 0 for x in xs)

実際の不具合なら、例えば`[0, -1]`のような入力へ縮みます。カスタム型は、単純なdataclassやenum、入れ子の構造を持たせると縮小しやすくなります。

Python / command generator
from dataclasses import dataclass
from hypothesis import strategies as st

@dataclass(frozen=True)
class Command:
    name: str
    amount: int

commands = st.builds(
    Command,
    name=st.sampled_from(["add", "remove"]),
    amount=st.integers(min_value=0, max_value=100),
)
失敗の読み順
1. どの性質が失敗したか
2. 縮小後の入力は何か
3. 失敗に必要な最小フィールドは何か
4. generatorは本番制約を表しているか
5. 入力を回帰テストへ固定するか
shrinkを無効にしてログを増やさない

巨大な失敗入力をそのまま保存するより、縮小器が原因の構造を見せるようにデータ型を変えます。失敗を再現する最小例は、設計レビューにも使えます。

seed・path・再現性

Hypothesisは失敗例をデータベースへ保存し、fast-checkはseedとpathを出力します。seedはデバッグの入口であり、仕様の証拠ではありません。generatorやライブラリ版が変わると、同じseedで入力が変わることがあります。

TypeScript / fast-check
import fc from "fast-check";

fc.assert(
  fc.property(fc.array(fc.integer()), xs => {
    return xs.length < 100;
  }),
  { seed: 12345, path: "0:1" },
);

CIログからseedをコピーするだけで終わらせず、縮小後の入力と性質名を固定fixtureにします。バージョンアップ時はfixtureが仕様として有効か確認し、古いseedに依存しすぎないようにします。

Python / regression
def test_regression_for_old_failure():
    # PBTが見つけた縮小済み入力を固定する
    assert normalize({"items": [0]}) == {"items": [0]}
再現記録の最小セット

性質名、入力・操作列、seedとpath、Hypothesis/fast-checkの版、対象コミット、環境、修正理由を一緒に残します。

ステートフルテスト

一回の関数呼び出しではなく、操作列で状態機械を揺さぶります。モデルは簡単であるほどよく、実装をそのままコピーして比較しないことが重要です。

Python / RuleBasedStateMachine
from hypothesis import strategies as st
from hypothesis.stateful import (
    RuleBasedStateMachine,
    invariant,
    rule,
)

class SetModel(RuleBasedStateMachine):
    def __init__(self):
        super().__init__()
        self.expected: set[int] = set()
        self.actual: set[int] = set()

    @rule(x=st.integers())
    def add(self, x: int):
        self.expected.add(x)
        self.actual.add(x)

    @rule(x=st.integers())
    def remove(self, x: int):
        self.expected.discard(x)
        self.actual.discard(x)

    @invariant()
    def agrees(self):
        assert self.actual == self.expected

TestSetModel = SetModel.TestCase

実装とモデルが同じコードなら、同じバグを共有して比較が無意味になります。モデルは集合・カウンタ・enumなど、独立した簡単な意味にします。

時間を操作として生成する

Python / fake clock
class FakeClock:
    def __init__(self):
        self.now = 0

    def advance(self, seconds: int):
        self.now += seconds

    def expired(self, deadline: int) -> bool:
        return self.now >= deadline

期限切れの不具合を見つけるには、時間を進める操作を生成します。本番のwall clockを直接読むのではなく、注入できるclockを使うと、PBTが再現可能になります。

モデルベーステストとオラクル

モデルベーステストでは、簡単な状態モデルに同じコマンド列を与え、実装の応答と状態を比較します。オラクルは実装と独立した判定基準です。

TypeScript / fast-check
import fc from "fast-check";

type State = "closed" | "open";
type Cmd = "open" | "close";

const step = (state: State, command: Cmd): State =>
  command === "open" && state === "closed" ? "open" :
  command === "close" && state === "open" ? "closed" :
  state;

fc.assert(fc.property(
  fc.array(fc.constantFrom<Cmd>("open", "close")),
  commands => {
    let model: State = "closed";
    for (const command of commands) {
      model = step(model, command);
    }
    return model === "closed" || model === "open";
  },
));
Python / independent oracle
from decimal import Decimal, localcontext
from hypothesis import given, strategies as st

@given(st.integers(-10_000, 10_000),
       st.integers(-10_000, 10_000))
def test_add_matches_decimal(a: int, b: int):
    with localcontext() as context:
        context.prec = 40
        assert Decimal(a) + Decimal(b) == Decimal(a + b)

オラクルも同じ実装・同じ丸め規則を共有していると、比較の独立性がありません。別実装、数学的に簡単なモデル、保存した仕様表など、異なる失敗経路を持つ基準を選びます。

依存するデータを生成する

Python / composite strategy
from hypothesis import strategies as st

@st.composite
def nonempty_pair(draw):
    xs = draw(st.lists(st.integers(), min_size=1))
    index = draw(st.integers(min_value=0, max_value=len(xs) - 1))
    return xs, xs[index]

依存するindexを先に独立生成すると、リスト長との矛盾を`assume`で捨てることになります。`composite`で同じ生成手順にすると、常に有効なペアを作れます。

TypeScript / command union
import fc from "fast-check";

type Command =
  | { kind: "add"; n: number }
  | { kind: "clear" };

const commandArb = fc.oneof(
  fc.record({ kind: fc.constant("add" as const), n: fc.integer() }),
  fc.constant({ kind: "clear" as const }),
);

fc.assert(fc.property(
  fc.array(commandArb),
  commands => {
    const values: number[] = [];
    for (const command of commands) {
      if (command.kind === "add") values.push(command.n);
      else values.splice(0);
    }
    return Array.isArray(values);
  },
));

union型でコマンドの引数不足をコンパイル時に見つけ、generatorが作る操作列の意味を明示します。型検査とPBTは別の証拠ですが、組み合わせると失敗入力を読みやすくできます。

メタモルフィックテスト

正解を直接計算しにくい処理では、入力を変換したときの出力関係を性質にします。ソート、単位変換、画像処理、コンパイラなどで使えます。

Python / metamorphic
from hypothesis import given, strategies as st

@given(st.lists(st.integers()))
def test_sort_translation(xs: list[int]):
    offset = 7
    left = sorted([x + offset for x in xs])
    right = [x + offset for x in sorted(xs)]
    assert left == right

入力を一様に平行移動しても、ソートの順序関係は保たれます。処理の仕様にこの関係が本当にあるかを確認し、可換でない業務処理へ誤って適用しません。

Python / commutativity
from hypothesis import given, strategies as st

@given(st.sets(st.integers()), st.sets(st.integers()))
def test_set_merge_order(a: set[int], b: set[int]):
    assert (a | b) == (b | a)
注文イベントを集合にしない

集合の和は可換ですが、注文・支払い・返金のイベントは順序が意味を持ちます。リストや操作列で生成し、順序を変えてよい操作だけに可換性を主張します。

CIで回す

Python / pytest
from hypothesis import given, settings, strategies as st

@settings(max_examples=300, deadline=None)
@given(st.lists(st.integers(), max_size=50))
def test_length_is_preserved(xs: list[int]):
    assert len(xs) == len(list(xs))

PRでは短い例数、夜間では広い探索という二層構成が実務的です。`deadline=None`は重い計算を許す設定であり、外部APIを無制限に呼んでよい意味ではありません。

CI設定
name: property-tests
on: [push, pull_request]

jobs:
  fast:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with:
          python-version: "3.12"
      - run: pip install hypothesis pytest
      - run: pytest -q tests/property

  nightly:
    runs-on: ubuntu-latest
    steps:
      - run: pytest -q tests/property --hypothesis-profile=nightly

CIの成功ログには、例数、profile、対象コミット、ライブラリ版を残します。失敗を単にretryして消すのではなく、縮小例をartifactと回帰テストへ移します。

アンチパターンと回避策

アンチパターンなぜ危険か回避
randomを直接使う失敗の入力を保存しにくいフレームワークのgeneratorとseed
例外が出ないだけを検査正しい出力や状態を保証しない往復・不変・モデル比較
assumeで大半を捨てる生成効率と範囲が見えないstructured strategy
generatorが本番制約と違う重要領域を生成しないAPI契約から設計
カバレッジ率を正しさと呼ぶ実行しただけで性質を見ない名前付きproperty
外部APIを全ケースで呼ぶ遅い・高価・flakyfakeと観測点
ケース数より反例の説明

良いPBTは、失敗したときに「どの性質が」「どの最小操作列で」「何を破ったか」を言えます。例数を増やす前に、失敗運用を作ります。

失敗例を育てる

  1. 生成器が作った縮小反例を保存する。
  2. バグの原因を一文で説明する。
  3. 最小例を固定回帰テストにする。
  4. 一般化できる性質をPBTへ残す。
  5. 仕様の欠陥ならTLA+やLeanの定義へ反映する。
  6. 再発時に同じseedだけでなく、入力と範囲を比較する。
失敗レコード
property: order_round_trip
input: {"id": "a", "cents": 0}
seed/path: 12345 / 0:1
library: hypothesis 6.x
commit: <record in CI>
cause: decoder dropped zero-valued field
fix: preserve explicit cents field
regression: tests/fixtures/order_zero.json

PBTの完了条件は、通過した回数ではなく、失敗をチームの共有知識へ変えたことです。次章の実例では、Web・数学・物理・ゲームをこの運用に接続します。

まとめ

PBTの品質は、ケース数ではなく性質・generator・shrink・失敗運用の組で決まります。往復、冪等性、モデル比較、許容誤差、単調性、操作列を題材に、実装を実際に揺さぶります。

生成器の範囲は保証範囲そのものです。seedを証拠と誤認せず、縮小入力とライブラリ版を保存し、次章の実例へ進みます。

用語集

property
多くの入力・操作に対して成立してほしい関係や不変条件。
generator
テスト対象の入力・コマンド列を作る戦略。
shrink
失敗を保ったまま入力を小さくする処理。
stateful test
複数の操作を順に実行し、状態の整合性を調べるテスト。
oracle
出力や状態が正しいか判定する独立基準。
metamorphic test
入力変換と出力変換の関係を調べるテスト。

理解度チェック

問1：PBTは何を先に決めてから入力を生成しますか。
性質を先に決めます。
問2：`assume`を多用すると何が起きますか。
入力を大量に捨て、効率と保証範囲が見えにくくなります。
問3：seedは証明の証拠ですか。
いいえ。再現の入口であり、generatorや版が変わると結果も変わり得ます。
問4：モデル比較でモデルを実装のコピーにしてはいけない理由は何ですか。
同じバグを共有し、比較の独立性が失われるためです。
