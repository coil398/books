Chapter 01 · 形式手法とテスト技法

Lean 4 の基礎

型・命題・証明・tacticを、コンパイラに検査されるプログラムとして学びます。

対象型付き言語とターミナルに慣れた人
成果物小さなLean証明を自力で実行できる
読む目安60〜90分

この章で学ぶこと

  • Leanプロジェクトを固定する
  • 命題を型と証明項として読む
  • 帰納法と自動化を使い分ける

前提知識

  • 関数型プログラミングの基礎
  • Nat・List・Optionの概念
  • CLI操作

所要時間の目安

最小ファイルを動かし、意図的に一つ壊してゴールを読みます。

環境を固定する

Lean 4は、証明をコンパイルする開発環境です。elanでtoolchainを固定し、Lakeで依存関係とビルドを管理すると、エディタ・CI・手元の結果を揃えやすくなります。

Shell
curl https://raw.githubusercontent.com/leanprover/elan/master/elan-init.sh -sSf | sh
source "${HOME}/.elan/env"
elan toolchain install leanprover/lean4:v4.19.0
elan default leanprover/lean4:v4.19.0
lake new fm-basics math
cd fm-basics

インストーラは親シェルの`PATH`を変更できないため、`source`を挟んでから`elan`を実行します。`stable`のような更新されるチャンネルは使わず、ここでは`leanprover/lean4:v4.19.0`を`lean-toolchain`へ保存してコミットします。教材を試すだけなら`lake new`でプロジェクトの雛形を作れますが、教材のコードは自動では`Main.lean`になりません。

版のずれは証明のずれになる

Lean本体、Mathlib、エディタ拡張の版が違うと、同じ名前の定理やsimpの挙動が変わることがあります。証明が通った画面のスクリーンショットではなく、CIのtoolchainを証拠にします。

プロジェクト確認
lean-toolchain
lakefile.toml
lake-manifest.json
Main.lean

`fm-basics/lean-toolchain`を次の一行で保存してからコミットします。

fm-basics/lean-toolchain
leanprover/lean4:v4.19.0

最小ファイルを読む

Lean 4
import Mathlib

def double (n : Nat) : Nat := n + n

theorem double_zero : double 0 = 0 := by
  simp [double]

example (n : Nat) : double n = n + n := by
  rfl

このコードを`fm-basics/Main.lean`として保存してから、プロジェクトディレクトリで検査します。

Shell
lake env lean Main.lean
lake build

`def`は計算可能な定義、`theorem`は名前を持つ証明付き宣言、`example`は検証後に名前を残さない宣言です。`by`の後ろはtactic列ですが、最終的には命題の型を持つ項を構築しています。

`rfl`が通るのは、定義を展開した左右が定義上同じだからです。`simp`は登録された簡約規則を使います。どちらも魔法の正しさを追加するのではなく、Leanがすでに持つ定義や定理を適用しています。

最初はexampleから

名前付き定理を長く書く前に、`example`でゴールとtacticを小さく試します。通ったらドメイン名を含む定理名へ昇格させ、レビューで検索できる形にします。

型と命題：Curry–Howard対応

Curry–Howard対応では、型を命題、値を証明、関数を含意として読むことができます。Leanを「数学専用言語」ではなく、型でプログラムを検査する言語として理解する入口です。

プログラム側論理側Leanでの読み方
型A命題AAを証明する値を作る
A → BAならばBAを受けてBを返す関数
A × B / A ∧ BAかつB二つの証明をペアにする
Sum A B / A ∨ BAまたはBどちらかのコンストラクタ
空型 / False偽この値があれば矛盾が出る
Lean 4
theorem implication (p q : Prop) : (p → q) → p → q := by
  intro hp h
  exact hp h

theorem and_left (p q : Prop) : p ∧ q → p := by
  intro h
  exact h.1

theorem and_build (p q : Prop) : p → q → p ∧ q := by
  intro hp hq
  exact ⟨hp, hq⟩

`intro`は含意や全称量化の仮定をコンテキストへ移し、`exact`は現在のゴールと型が一致する項を置きます。証明が読めないときは、まず「今のゴール」と「手元の仮定」を日本語に直します。

命題を型として読む

Lean 4
import Mathlib

#check Nat
#check (fun n : Nat => n + 1)
#check ∀ n : Nat, n + 0 = n
#check ∃ n : Nat, n = 3

theorem exists_three : ∃ n : Nat, n = 3 := by
  exact ⟨3, rfl⟩

`∀ n, P n`は任意のnを受け取ってP nの証明を返す関数です。`∃ n, P n`は値nと、その値についての証明をペアにします。仕様を型にすると、呼び出し側が前提を渡さない限り関数を利用できない設計を作れます。

場合分けとコンストラクタ

Lean 4
theorem option_cases (x : Option Nat) :
    x = none ∨ ∃ n, x = some n := by
  cases x with
  | none => exact Or.inl rfl
  | some n => exact Or.inr ⟨n, rfl⟩

`cases`はデータ型の全コンストラクタを扱わせます。入力に新しいコンストラクタを追加すると、証明の未処理分岐がコンパイルエラーとして現れるため、仕様の漏れをレビューできます。

基本tacticを使い分ける

simp：定義済みの簡約

Lean 4
theorem add_zero (n : Nat) : n + 0 = n := by
  simp

theorem list_map_id (xs : List α) : xs.map id = xs := by
  simp

`simp`は便利ですが、登録規則が増えると意図が追いにくくなることがあります。再現性やレビュー可能性が重要な箇所は`simp only [規則]`で使う規則を絞ります。

rw：向きを明示した書き換え

Lean 4
theorem rewrite_demo (a b c : Nat) (h : a = b) :
    a + c = b + c := by
  rw [h]

theorem rewrite_reverse (a b : Nat) (h : a = b) :
    b = a := by
  rw [h]

`rw [h]`はゴール中のaをbへ書き換えます。似た式が変わらない場合は、等式の向き、暗黙引数、型クラスの選択を確認します。

apply・constructor・exact

Lean 4
theorem trans_demo (a b c : Nat)
    (hab : a = b) (hbc : b = c) : a = c := by
  apply Eq.trans hab
  exact hbc

theorem pair_demo (p q : Prop) (hp : p) (hq : q) : p ∧ q := by
  constructor
  · exact hp
  · exact hq

`apply`はゴールに合う定理を選び、残りの前提を新しいゴールにします。`constructor`は構造の各フィールドを別ゴールに分解します。短い`exact`を積み重ねると、証明の設計意図が残ります。

帰納法で無限のデータを扱う

帰納法は、基底ケースと帰納ステップを証明することで、自然数やリストの全要素について性質を示します。帰納仮定は、ステップで使える過去の証拠です。

Lean 4
theorem add_zero_induction : ∀ n : Nat, n + 0 = n := by
  intro n
  induction n with
  | zero => rfl
  | succ n ih =>
      simp [Nat.succ_add, ih]

theorem length_append (xs ys : List α) :
    (xs ++ ys).length = xs.length + ys.length := by
  induction xs with
  | nil => simp
  | cons x xs ih => simp [ih]

リストの`cons`ケースでは、先頭要素xと残りxsに分かれ、xsについての`ih`を使います。証明が長くなるときは、帰納対象を先に考えます。`xs`全体を固定したまま別の引数だけを帰納すると、必要な一般性を失うことがあります。

帰納法の前に定義を確認する

関数の再帰方向とデータ型のコンストラクタが合わないと、ゴールが扱いにくくなります。まず小さな`#check`と`example`で、どの引数が構造的に減っているか確認します。

Lean 4
def sumTo : Nat → Nat
  | 0 => 0
  | n + 1 => n + 1 + sumTo n

theorem sumTo_zero : sumTo 0 = 0 := by
  rfl

theorem sumTo_one : sumTo 1 = 1 := by
  simp [sumTo]

算術と自動化

tactic向いている問題注意
omega線形のNat・Int不等式積や関数の意味は別にする
ring可換環の多項式恒等式単位や型変換は自動で決まらない
linarith線形不等式の前提非線形項には弱い
norm_num具体的な数値の簡約巨大な計算はコンパイル時間に注意
decideDecidableな有限命題実行可能な判定のコストを確認
Lean 4
import Mathlib

example (x y : Int) (h₁ : x ≤ y) (h₂ : y ≤ x) : x = y := by
  omega

example (x y : ℚ) : (x + y) * (x - y) = x^2 - y^2 := by
  ring

example : (12345 : ℤ) + 55 = 12400 := by
  norm_num

example : (37 : Nat) < 100 := by
  decide

自動化が通らないこと自体が設計信号になる場合があります。`Nat`のunderflowを許していないか、値域が`Int`なのか、単位を型で表すべきかを見直します。tacticを増やす前に、ゴールの意味を明確にします。

型で不正状態を表しにくくする

命題を毎回引数で要求する代わりに、構造体のフィールドとして不変条件を持たせる方法があります。値を作る時点で証明を要求するため、利用側の分岐を減らせます。

Lean 4
import Mathlib

structure Quantity where
  value : ℚ
  nonnegative : 0 ≤ value

def Quantity.add (a b : Quantity) : Quantity :=
  { value := a.value + b.value
    nonnegative := by
      linarith [a.nonnegative, b.nonnegative] }

example (a b : Quantity) :
    (Quantity.add a b).nonnegative := by
  exact (Quantity.add a b).nonnegative

ただしフィールドを公開すると、利用側が不変条件を直接作るための設計が変わることがあります。スマートコンストラクタ、opaqueな抽象、validatorの境界を検討します。

implicit引数とautoImplicit

Lean 4
import Mathlib

def identity (x : α) : α := x

example (x : Nat) : identity x = x := by
  rfl

set_option autoImplicit false
def explicitIdentity {α : Type} (x : α) : α := x

教材では自動暗黙変数が便利ですが、公開ライブラリでは`set_option autoImplicit false`が誤記を発見します。型の曖昧さを放置すると、別の型クラスが選ばれ、証明が版変更に弱くなることがあります。

証明が通らないときの読み方

Lean 4
import Mathlib

example (n : Nat) : n + 1 = 1 + n := by
  simpa [Nat.add_comm]
エラー典型原因最初の対処
type mismatch項の型が違う`#check`と型注釈を追加
unsolved goals前提・場合分け不足`intro`、`cases`、`induction`を小さく試す
unknown constantimportや名前が違う`#check`とMathlibの検索
tactic failedtacticの対象外手動変形、別tactic、補題化
maximum recursion定義・simp規則のループ`simp only`と定義の見直し

ゴール画面を読み飛ばさないでください。失敗した証明を最小の`example`へ切り出し、定義・前提・結論のどこが不一致かを分けます。長い証明の最後でエラーを追うより、途中の型を`#check`する方が速いことが多いです。

Lean 4
import Mathlib

#check List.map
#check List.map_append
#check Nat.add_comm
#check Finset.card
#check Set.mem_inter_iff
証明の失敗は設計レビューになる

前提が多すぎる、casesが増えすぎる、型変換で詰まるという症状は、APIの不変条件や値域の選び方を見直すサインです。

sorryを証拠にしない

Lean 4
import Mathlib

theorem future_proof : 2 + 2 = 4 := by
  sorry

`sorry`は仮の証明を受け入れ、警告を出します。設計中に依存関係を先に進める用途はありますが、保証の証拠ではありません。CIでは`sorry`の利用を警告として拾い、リリース対象からゼロにします。

Shell
if ! lake build > build.log 2>&1; then
  cat build.log
  exit 1
fi
cat build.log
! rg -q "declaration uses 'sorry'" build.log
未証明を完了扱いしない

定理名が存在しても、証明本体に`sorry`が残るなら、プロジェクトの保証は未完了です。issue、担当者、期限を記録し、警告を見逃さないCIにします。

証明と実行可能コードを分ける

Lean 4
import Mathlib

def factorial : Nat → Nat
  | 0 => 1
  | n + 1 => (n + 1) * factorial n

theorem factorial_two : factorial 2 = 2 := by
  norm_num [factorial]

def main : IO Unit := do
  IO.println s!"2! = {factorial 2}"

数学的な定義とIOを分離すると、純粋な定理を実装の核へ置きやすくなります。実行方法はプロジェクトの構成に依存するため、`lake env lean`で宣言を検査し、必要ならLakeの実行ターゲットを追加します。

Shell
lake new lean-demo math
cd lean-demo
cp /path/to/Main.lean Main.lean
lake env lean Main.lean
lake build

教材の複数例を一つの`Main.lean`へ貼ると、定理名の衝突やimportの違いが出ます。最初は章の例を一つずつ`example`にし、動いた後でnamespaceとファイル分割を行います。

証明を設計へ戻す

症状設計上の問い改善の方向
omegaが通らないNatとIntの意味は合っているか値域と負数の契約を明記
ringが通らない単位と変換はどこにあるか量の型や補題を追加
casesが増え続ける状態をinductiveにするか不正状態を型で隠す
前提が多い構造体に不変条件を持たせられるかsmart constructorを検討
移植propertyが失敗本番定義と定理定義は同じか対応表とfixtureを残す

証明の難しさは、数学の難しさだけでなくAPIの設計を反映します。補題の境界がドメインの境界になっているか、定理名がレビューで検索できるか、証明の前提がプロダクト仕様として説明できるかを確認します。

Lean 4
import Mathlib

namespace Cart

def total (xs : List Nat) : Nat := xs.sum

theorem total_append (xs ys : List Nat) :
    total (xs ++ ys) = total xs + total ys := by
  simp [total]

end Cart

namespaceは別ドメインの同名関数を分けます。数学の一般定理をコピーするより、ドメイン名を含む薄い補題を用意すると、後からコードと仕様の対応を追えます。

章末演習

リスト変換の長さを保存する

Lean 4
import Mathlib

theorem list_length_map (f : α → β) (xs : List α) :
    (xs.map f).length = xs.length := by
  induction xs with
  | nil => rfl
  | cons x xs ih => simp [ih]

保証したいのは`map`が要素数を変えないことです。ページサイズ、バッチ上限、メッセージ分割に関わるため、単純な補題でも業務上の意味があります。

証明付きのhead

Lean 4
import Mathlib

def head? : (xs : List α) → xs ≠ [] → α
  | x :: _, _ => x
  | [], h => (h rfl).elim

空リストを受け取らないAPIにするか、`Option`を返すか、`Nonempty`構造体を使うかは設計判断です。証明を追加すること自体が目的ではなく、不正状態がどの境界で扱われるかを明確にします。

  • 一つの定理を`example`で試してから名前付き定理へ移す。
  • 一行だけ定義を変え、どのゴールが失敗するか読む。
  • 値域をNatからIntへ変えると、前提とtacticがどう変わるか確認する。
  • 自動化が通った理由を、使った定理名または型で説明する。

まとめ

Leanでは、型・命題・証明・プログラムが同じ検査の対象になります。`intro`、`exact`、`rw`、`cases`、`induction`、算術tacticを小さく組み合わせ、定義と前提を読みやすく保ちます。

証明が通ることだけでなく、どの前提を置いたか、`sorry`がないか、実装との対応はどこで確認するかを運用に含めます。次章では、数学・物理・ゲーム・Webの中核をLeanへ切り出します。

用語集

toolchain
Lean本体・コンパイラ・標準ライブラリの組み合わせ。
tactic
ゴールを変形し、最終的な証明項を構築するコマンド。
命題（Prop）
証明できるかどうかを型として表したもの。
帰納法
基底ケースと帰納ステップから全ての構造を証明する方法。
型クラス
共通の操作や性質を暗黙引数として解決する仕組み。
smart constructor
不変条件を満たす証明を要求して値を作る入口。

理解度チェック

問1：`rfl`と`simp`の違いを説明してください。
`rfl`は定義上同じもの、`simp`は登録された簡約規則での変形を示します。
問2：`intro`はどのようなゴールで使いますか。
含意や全称量化の仮定をコンテキストへ移すときです。
問3：リストの長さ保存で帰納法が必要になる理由は何ですか。
任意のリストをnilとconsに分解し、残りのリストについての帰納仮定を使うためです。
問4：`sorry`をCIで許してはいけない理由は何ですか。
宣言は存在しても、実際の証明項がないため、保証の証拠にならないからです。
