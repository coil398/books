形式手法とテスト技法

Lean 4・TLA+・Property-Based Testingを、実務で「何を保証し、どこに穴が残るか」から学ぶ日本語HTML教科書です。

対象現役エンジニア、形式手法は初めて
成果物三手法の役割と読み進め方
読む目安20〜30分

この章で学ぶこと

  • 保証を対象・前提・性質・証拠へ分解する
  • 三手法の境界と導入順序をつかむ
  • 自分の課題から次章を選ぶ

前提知識

  • 型付き言語の基礎
  • ユニットテストの読解
  • ターミナルを使う経験

所要時間の目安

まずはこの表紙と00章を読み、過去障害を一つ題材にします。

この本の読み方

このHTML版は、形式手法を「数学者だけが使う証明道具」としてではなく、現役のソフトウェアエンジニアが設計レビューとCIに組み込むための教科書としてまとめたものです。形式手法とは、仕様や実装を数学的に扱い、テストだけでは届きにくい範囲を証拠にする技術群です。

最初からすべてを証明する必要はありません。まず、壊れると高価な性質を一つ選び、対象・前提・保証・証拠を分けて書きます。その一文が書ければ、どの道具を使うかはかなり明確になります。

最初の30分でやること

過去の障害を一つ選び、「どの状態で」「どの順番で」「何が起きたか」を短く記録してください。二重購入ならTLA+、金額計算ならLean、未知の入力ならPBTが入口になります。

三手法を1画面で比較する

三つの技術は競合する製品ではなく、異なる層を担当するレンズです。Leanは定義と証明項を検査し、TLA+は状態遷移を列挙し、Property-Based Testing（PBT）は実装を生成入力で実行します。

手法主な問い網羅する範囲証拠の形得意な失敗
Leanこの式・関数は前提から必ず性質を満たすか形式化した全入力型検査済みの定理丸め、集計、型の不整合
TLA+ / TLCこの状態から競合や停止が起きないか有限に切った到達可能状態反例トレースまたは検査成功競合、原子性、再試行、進行
PBT実装を多様な入力・操作列で動かすとどうか生成された有限サンプル縮小入力、seed、回帰fixture境界値、シリアライズ、接続不備

「100万件通ったから証明済み」「TLCが通ったから本番も安全」「Leanの定理があるから移植コードも同じ」という読み替えは危険です。証拠には必ず、対象・前提・範囲・ツール版を添えます。

保証を四つに分解する

対象・前提・性質・証拠

「APIは安全」のような文は、レビューで反証も再現もできません。次の四つ組にすると、何を調べているかが見えるようになります。

項目書く内容購入フローの例

証拠定理、モデル検査、テスト結果TLCのSafety、PBTの反例なし

在庫1のモデルで安全でも、在庫100やキャンセルを含む実装の安全を自動的に意味しません。範囲が変わったときは、モデル定数・generator・定理のどれを更新するかをレビューします。

Leanの役割：計算の核を全入力で固定する

Leanは証明支援系です。定義・型・命題を一つの言語で書き、コンパイラが受け入れた証明項だけを残します。純粋関数、データ構造、保存量、権限表のように、入力と出力の関係を数学的に切り出せる対象に向きます。

Lean 4
import Mathlib

def subtotal (prices : List Nat) : Nat := prices.sum

theorem subtotal_append (xs ys : List Nat) :
    subtotal (xs ++ ys) = subtotal xs + subtotal ys := by
  simp [subtotal]

ここで保証しているのは「明細を二つに分けて計算しても小計が変わらない」という恒等式です。DBが二重に呼ばれないことや、画面に正しい通貨記号が出ることは、この定理の対象外なので別の証拠に置きます。

定理と本番実装を同一視しない

別言語へ手書き移植した関数がLeanの定義と同じ意味だとは限りません。移植境界にはPBTやgolden testを置き、さらに重要なら生成コードやrefinementの対応を管理します。

TLA+の役割：順番と同時実行を壊してみる

TLA+は状態遷移を中心に仕様を書きます。`Init`が初期状態、`Next`が一回のアクション、`Spec`が実行列です。モデル検査では、定数を小さく限定した状態空間をTLCが探索し、性質を破る最短に近いトレースを返します。

TLA+
---- MODULE Shop ----
EXTENDS Naturals

CONSTANT Users, InitialStock
VARIABLE stock, orders

Init == /\ stock = InitialStock
        /\ orders = [u \in Users |-> "none"]
Purchase(u) == /\ orders[u] = "none"
                /\ stock > 0
                /\ stock' = stock - 1
                /\ orders' = [orders EXCEPT ![u] = "paid"]
Next == \E u \in Users : Purchase(u)
Safety == stock >= 0
Spec == Init /\ [][Next]_<<stock, orders>>
================================

このモデルが保証するのは、指定したユーザー集合・在庫数・一アクションの粒度で到達可能な状態にSafety違反がないことです。ネットワーク遅延、DBの分離レベル、実際のタイムアウトを落としているなら、その境界を別途モデル化するかPBTへ渡します。

TLCの成功は「範囲付きの成功」

定数を一人にすると競合が消えます。まず二人・容量一で反例を探し、その後に必要な変数だけ増やします。状態爆発を避けるために小さくするのと、競合を消すために小さくするのは別です。

PBTの役割：実装境界を大量に揺さぶる

PBTは「ランダムな入力を投げる」だけではありません。先に性質を決め、現実の制約を持つジェネレータで入力を作り、失敗時はshrinkで原因の小さい例へ縮めます。

Python
from hypothesis import given, strategies as st

def encode_total(xs: list[int]) -> int:
    return sum(xs)

@given(st.lists(st.integers(min_value=0), max_size=30))
def test_append_property(xs):
    assert encode_total(xs + []) == encode_total(xs)

この例は空リストを追加しても結果が変わらないという性質を、実装上で何度も確認します。生成器が負数を除外しているなら、負数を含む契約を保証してはいません。生成器の制約はテストコードの細部ではなく、保証範囲そのものです。

PBTの成果物は失敗入力

テストが通ったというログより、縮小後の入力・seed・ライブラリ版・性質名を残す方が、次の修正に役立ちます。反例は固定回帰テストに昇格させ、一般性はPBTへ残します。

同じ障害を三つの角度で読む

在庫一個を二人が買う

要求を「二人の購入操作が同時に来ても在庫が負にならない」とします。この文を、設計・実装・計算の三つに分けると、各技術の責任範囲が重なりすぎません。

層具体的な観測点適した証拠
プロトコル予約と減算が一つの原子アクションかTLA+の反例トレース
実装同じキーの再送、辞書更新、エラー応答PBTの操作列
計算小計・割引・税の恒等式Leanの定理とPBTの移植確認
Python
class Shop:
    def __init__(self, stock: int):
        self.stock = stock
        self.orders: dict[str, str] = {}

    def purchase(self, user: str) -> bool:
        if self.stock <= 0 or user in self.orders:
            return False
        self.stock -= 1
        self.orders[user] = "paid"
        return True

このPythonは単一スレッドの教育用です。`if`と減算の間に別リクエストが入れば、モデルの一アクションと実装のatomicityがずれます。実際のDBでは条件付き更新、トランザクション、冪等キーの一意制約を同時に検討します。

Lean 4
import Mathlib

def discount (amount rate : Nat) : Nat :=
  amount * rate / 100

theorem discount_le_amount (amount rate : Nat) (h : rate <= 100) :
    discount amount rate <= amount := by
  unfold discount
  exact Nat.div_le_of_le_mul (Nat.mul_le_mul_left amount h)

割引率の範囲はLeanで証明できる一方、決済サービスが二回呼ばれないことは別問題です。証明できる核と、実行順序を扱うモデルを無理に一つへ詰め込みません。

失敗モードから入口を選ぶ

失敗モード最初の問い入口次に足すもの
負の在庫・二重予約同時操作の順序は何かTLA+PBTで実装再現
丸めが一円ずれる値域と丸め規則は何かLeanPBTで移植・境界
未知のJSONで落ちる入力スキーマと往復は何かPBTLeanで型の核
失効後に利用できる状態遷移に戻り道があるかTLA+PBTで時計・キャッシュ
無限に待つ公平性をどう仮定するかTLA+ liveness監視・タイムアウトテスト

迷ったら、道具の流行ではなく「最も高価な失敗を最小にできるか」で決めます。最初の成果物は、完成した巨大モデルではなく、チームが説明できる小さな反例です。

順序のある判断

1. 破ると高価な性質を一つ選ぶ。2. 入力・状態の範囲を決める。3. 最小の証拠を作る。4. 反例を修正する。5. 失敗範囲を記録する。

現実的な導入ワークフロー

  1. 障害や設計レビューから、保証したい文を日本語で書く。
  2. 入力・ユーザー数・時計・外部依存の前提を明記する。
  3. PBTで実装境界の例と縮小反例を集める。
  4. 競合・再試行・公平性がある部分だけをTLA+に縮約する。
  5. 純粋な金額・権限・データ変換をLeanへ切り出す。
  6. CIで証拠を別ジョブにし、どの範囲を検査したか保存する.

この順序は絶対ではありません。TLA+に慣れたチームならモデルから始めてもよいし、既存のLean資産があるなら定理から始めてもよいでしょう。重要なのは、ツール導入そのものを成功条件にしないことです。

証拠の記録
tool: TLC
model: Users = {"alice", "bob"}, InitialStock = 1
property: stock >= 0
result: no counterexample
implementation-gap: DB transaction and cache not modeled
owner: checkout-team
recorded-at: 2026-08-01

記録には対象コミット、ツール版、モデル定数、PBTの例数、Leanのtoolchainも加えます。成功ログだけでなく、形式化しなかった部分を明示することが再現性の一部です。

よくある落とし穴を先に知る

仕様を実装の写経にする

本番コードをそのままTLA+へ翻訳すると、同じ条件分岐のバグを共有してしまいます。モデルは異なる抽象化で、何が原子で何が順序を持つかを表します。

生成器がきれいすぎる

常に正しいJSONしか作らないgeneratorは、未知フィールド、空文字、Unicode、最大長、重複キーを見ません。valid入力の性質とinvalid入力の拒否を分けて生成します。

証明の前提を隠す

Leanで`rate <= 100`を仮定したなら、そのvalidatorが実装入口で必ず通るかをPBT・型・契約で確認します。定理の前提はコメントではなく設計の境界です。

反例を責任追及に使わない

短い反例は、個人のミスを示すのではなく、状態の切り方・APIの契約・トランザクション境界を改善する設計資料です。

読む順序のガイド

あなたの目的読む順序到達点
全体像を知りたい00 → 07保証範囲を説明できる
Leanを使いたい00 → 01 → 02 → 07純粋関数の定理をCIに置ける
並行性を設計したい00 → 03 → 04 → 07反例トレースから実装契約を作れる
既存APIを揺さぶりたい00 → 05 → 06 → 07generatorと縮小例を運用できる
三つを比較したい各基礎章を先に読み、07へ同じ題材を層別に検証できる

一章を読み終えたら、コードを全部理解するより、性質を一文で言い直してください。その後、一行だけ壊して、どの証拠が失敗するかを確認すると学習が定着します。

最初の練習ループ
要求を一文にする
  -> 対象と前提を分ける
  -> 最小コードを書く

  -> 回帰テストと設計記録に残す

環境構築へのショートカット

環境を一度に全部揃える必要はありません。まず、手元の言語と課題に対応する章の最小プロジェクトだけを作ります。各ツールの版はリポジトリに固定し、教材のコードと実際のプロジェクトを混ぜないようにします。

試したいこと最初に開く章最小の入口

競合する状態遷移03 TLA+ 基礎TLCの最小モデル

インストールができない環境でも、本文の性質を先にレビューできます。形式化の前提を文章にし、後から実行可能なコードへ移すことも正しい学び方です。

ショートカットの使い分け

純粋計算は01章、領域別のLean例は02章、状態遷移は03〜04章、実装を揺さぶる例は05〜06章、同じEC題材を一気通貫で読むなら07章へ進んでください。

  1. 章を一つ選び、最小コードをそのまま保存する。
  2. 正常系を確認し、保証したい性質を一文に書き直す。
  3. 意図的に一か所だけ壊し、どの証拠が赤くなるかを見る。

この反復を一回できれば、ツールの機能を暗記するより先に、保証範囲と未保証の境界を会話できるようになります。チームで読むときは、反例を直す担当者も最初に決めてください。

読むときの合言葉 何を対象にするか。 どんな前提を置くか。 何が破れないと嬉しいか。 どの証拠がそれを支えるか。

まとめ

Leanは形式化した関数や命題を全入力の形で固定し、TLA+は有限モデルの状態遷移を網羅し、PBTは実装を生成入力と操作列で揺さぶります。三つの成功は同じ意味ではありません。

実務では、対象・前提・性質・証拠を記録し、形式化しない外部依存をテスト・監視・運用手順へ置きます。最も高価な失敗を最小化するところから始めれば、形式手法は大きな研究プロジェクトではなく、設計の解像度を上げる小さな道具になります。

用語集

形式手法
仕様や実装を数学的な対象として扱い、証明・モデル検査などで性質を確認する技術群。
不変条件
状態が遷移しても常に成立してほしい述語。Safetyの中心になる。
反例
性質を破る入力、状態、または状態列。修正の出発点になる。
原子性
途中状態を他の操作から観測・割り込みされない一つの操作単位。
オラクル
出力が正しいかを判定する、実装とは独立した基準。
refinement
抽象仕様の振る舞いを、具体的な実装が満たす対応づけ。

理解度チェック

問1：Lean、TLA+、PBTの主な対象を一言ずつ説明してください。
Leanは定義・命題、TLA+は状態遷移、PBTは実装の生成入力・操作列です。
問2：TLCが通ったとき、必ず本番コードも安全だと言えないのはなぜですか。
有限定数、抽象化、アクションの原子性など、モデルが落とした要素があるためです。
問3：「保証」を記録するときの四つの項目は何ですか。
対象、前提、性質、証拠です。
問4：二重購入・丸め誤差・未知JSONの最初の入口をそれぞれ選んでください。
順序ならTLA+、計算式ならLean、実装境界ならPBTが自然な入口です。
