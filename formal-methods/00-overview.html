Chapter 00 · 形式手法とテスト技法

3手法の地図

Lean・TLA+・Property-Based Testingが、どの種類の不確実さをどう扱うかを、同じEC題材で比較します。

対象形式手法を初めて使うエンジニア
成果物課題に対する最初の入口を選べる
読む目安35〜45分

この章で学ぶこと

  • 保証を範囲付きで書く
  • 三手法の役割と限界を区別する
  • 失敗モードから導入順を決める

前提知識

  • 型付き言語の経験
  • ユニットテストの読解
  • 基本的なCIの概念

所要時間の目安

比較表を読み、縦切りの例を一つチームの題材に置き換えます。

「正しい」を分解する

「バグがない」は大きすぎる主張です。保証を語るときは、対象・前提・入力範囲・時間範囲・証拠を分けます。この章では、Lean、TLA+、PBTが同じ「品質」という言葉に対してどこを担当するかを地図にします。

三つの技術を先に覚える必要はありません。まず、自分のサービスで失敗すると高価な性質を一つ選び、その性質を他の人が反証できる文章にします。

この章の読み方

コードを細部まで暗記するより、同じ性質が三つの道具でどう姿を変えるかを見てください。性質の形が変わると、証拠の範囲も変わります。

三手法の全体比較

手法主な対象何を網羅するか結果代表的なコスト
Lean純粋関数・型・定理形式化した全入力前提から結論を導く証明モデル化と証明の初期費用
TLA+ / TLC並行・分散の状態遷移有限に切った到達状態不変条件の成功、または反例状態爆発と抽象化の判断
PBT実装・API・状態機械生成された入力と操作列失敗の縮小例、またはサンプル通過generatorとshrinkの設計

Leanの「全入力」、TLCの「有限状態の全探索」、PBTの「生成したケース」は、同じ全てではありません。ここを混ぜると、テストのケース数を証明と呼んだり、抽象仕様の成功を本番実装の成功と誤認したりします。

保証を書く型
対象 = 何の関数・状態・境界を調べるか
前提 = 値域、環境、モデルの制約は何か
性質 = 常に、いつか、往復、単調性のどれか
証拠 = 定理、TLC、PBT、レビュー、監視のどれか
範囲 = 何をモデル化せず、どこへ渡すか

同じ合計処理を三つで読む

例示テストとPBT

Python
def total(prices: list[int], tax: int) -> int:
    return sum(prices) + tax

def test_total_example():
    assert total([100, 200], 30) == 330

例示テストは具体的な契約を伝えますが、空リスト、負数、巨大値、税率の意味は別の入力です。PBTなら、まず自然数の範囲を明示した性質を実行できます。

Python / Hypothesis
from hypothesis import given, strategies as st

@given(st.lists(st.integers(min_value=0), max_size=20),
       st.integers(min_value=0))
def test_total_agrees_with_reference(xs, tax):
    assert total(xs, tax) == sum(xs) + tax

この性質の対象はPythonの実装そのものです。ただしgeneratorの範囲外、例えば負数を許す契約や固定幅整数のオーバーフローは対象外です。

Leanで同じ関係を定義する

Lean 4
import Mathlib

def total (prices : List Nat) (tax : Nat) : Nat :=
  prices.sum + tax

theorem total_spec (prices : List Nat) (tax : Nat) :
    total prices tax = prices.sum + tax := by
  rfl

`rfl`は定義を展開すると左右が同じになることを示します。単純な定理でも、すべての`prices`と`tax`が対象になる点は例示テストと違います。実装との対応はまだ別に必要です。

Leanが得意な範囲と残る穴

純粋な核

Leanは、入力から出力への関数、帰納的データ構造、算術恒等式、型で不正状態を隠す設計に向きます。例えば空でないページだけを受け取る型は、呼び出し側へ前提を押し出せます。

Lean 4
import Mathlib

structure NonEmptyPage (α : Type) where
  items : List α
  nonempty : items ≠ []

def first {α : Type} (page : NonEmptyPage α) : α :=
  page.items.head page.nonempty

`List.head`へ空リストではない証明`page.nonempty`を渡すため、到達不能な空分岐を手作業で精緻化する必要がありません。

一方、DBの分離レベル、時計、ネットワーク、OSスケジューラを自動で網羅するわけではありません。これらを形式化するなら追加のモデルと仮定が必要で、しばしばTLA+やPBTの境界に置く方が費用対効果に合います。

Leanの定理は移植の証明ではない

PythonやTypeScriptへ手書き移植した関数がLeanの定義と同じだと自動的に分かるわけではありません。中核関数のproperty、golden fixture、生成コードなどを接続証拠として残します。

TLA+が得意な順序・競合・進行

状態を値の組として書く

TLA+では状態変数の組がシステムのスナップショットです。アクションは現在状態と次状態を関係づけ、プライム記号は次状態の値を表します。

TLA+
---------------- MODULE Counter ----------------
EXTENDS Naturals

VARIABLE count

Init == count = 0
Inc == count' = count + 1
Next == Inc
Spec == Init /\ [][Next]_count
===============================================

`Init`は開始点、`Next`は一歩の遷移、`Spec`は停止（stuttering）を含む実行列です。`TypeOK`や業務不変条件をTLCのチェック対象にすると、値の範囲だけでなく保存や所有権も検査できます。

SafetyとLiveness

性質日本語の問い反例の形注意
Safety悪いことは決して起きないか有限の状態トレース不変条件と原子性を読む
Liveness良いことはいつか起きるか停滞または無限ループ公平性の仮定が必要
TypeOK値は想定型か型外の状態業務ルールだけでは不十分
Nextが弱すぎると成功は無意味

`Next == TRUE`は何でも起きる仕様です。検査が通ってもシステムの契約を守ったとは言えません。変化しない変数には`UNCHANGED`を明示し、一アクションの粒度をレビューします。

PBTが得意な実装境界

PBTはパーサ、JSON、SDK、APIバリデーション、時計を注入した状態機械など、実装を実際に動かせる境界に強い技法です。重要なのは「何をランダムにするか」ではなく、性質を先に名前付けすることです。

性質パターン例破れると起きること
往復decode(encode(x)) = x保存データが再読込で変わる
冪等f(f(x)) = f(x)再送で二重決済・二重登録
可換merge(a,b) = merge(b,a)順序に依存しない処理が逆転
単調性強化後の結果が悪化しない権限・スコア・上限の逆転
モデル比較簡単な仕様と実装が一致状態遷移の接続ミス
Python / Hypothesis
from hypothesis import given, strategies as st

@given(st.text())
def test_text_round_trip(value: str):
    encoded = value.encode("utf-8")
    decoded = encoded.decode("utf-8")
    assert decoded == value

生成器にない入力は、通過したpropertyの対象外です。`assume`で大半を捨てるより、制約をstrategyの構造に入れます。shrinkされた反例は、ライブラリ版やseedと一緒に回帰fixtureへ移します。

在庫購入を縦に切る

三手法を一つのECの購入フローへ割り当てます。TLA+は競合と冪等キー、PBTはJSON・操作列・実装境界、Leanは小計・割引・権限といった純粋な計算を担当します。

TLA+
EXTENDS Naturals

CONSTANT Users, InitialStock
VARIABLE stock, orders

Init == /\ stock = InitialStock
        /\ orders = [u \in Users |-> "none"]
Purchase(u) == /\ orders[u] = "none"
                /\ stock > 0
                /\ stock' = stock - 1
                /\ orders' = [orders EXCEPT ![u] = "paid"]
Next == \E u \in Users : Purchase(u)
Safety == stock >= 0
Spec == Init /\ [][Next]_<<stock, orders>>
Python
from dataclasses import dataclass

@dataclass(frozen=True)
class Line:
    cents: int

def subtotal(lines: list[Line]) -> int:
    return sum(line.cents for line in lines)

def accepts(lines: list[Line]) -> bool:
    return all(line.cents >= 0 for line in lines)
Lean 4
import Mathlib

def subtotal (prices : List Nat) : Nat := prices.sum

theorem subtotal_append (xs ys : List Nat) :
    subtotal (xs ++ ys) = subtotal xs + subtotal ys := by
  simp [subtotal]

同じECの話でも、TLA+のSafety違反とLeanの未証明ゴールとPBTの縮小入力は別の証拠です。一つが成功したから他を省略するのではなく、境界でつなぎます。

コストと導入順序

段階行うこと成果物失敗時の判断
1障害から性質を一文にする対象・前提・性質仕様の曖昧さを修正
2PBTで実装境界を観測縮小反例・fixturegeneratorの穴を直す
3TLA+で最小競合を探索状態トレース原子性と抽象化を直す
4Leanで計算核を固定定理・型定義と前提を分ける
5CIとレビューへ接続再現可能な証拠版・範囲・担当を記録

すべてを形式化しようとすると失速します。高価な失敗、再利用される性質、過去に反例が出た境界から深くします。性能、UIの見た目、外部サービスの実応答は、監視・負荷試験・統合テストへ置くことも正しい設計です。

導入計画
第1週: 過去障害を三つ選び、性質を文章化
第2週: PBTで入力境界を固定
第3週: TLA+で二人・容量一の競合を検査
第4週: 金額または権限の純粋関数をLean化
毎週: 反例を回帰テストと設計文書へ移す

誤解とアンチパターン

「TLCが通ったので本番も安全」

モデルの抽象化が本番と一致する範囲でのみ安全です。キューを集合にしたなら、重複・順序・再配信を落としている可能性があります。

「ケース数を増やせば証明に近づく」

ケース数は未生成領域を消しません。性質・generator・shrinkの品質を先にレビューします。

「Leanの定理があるから実装も同じ」

定義の対応と境界の証拠が必要です。整数幅、丸め、外部依存、例外の意味が移植で変わります。

反例を保存する

モデル定数、入力、状態列、seed、ライブラリ版、修正した設計判断を残すと、次の変更で同じ穴を掘り直さずに済みます。

空欄が埋まらないときは、ツール選定を先送りしても問題ありません。形式手法は曖昧な要求を魔法のように正しくするのではなく、曖昧さを反証可能な形で見せるための道具です。

まとめ

この地図を使うと、ツールの選択を「何が流行っているか」ではなく「どの失敗をどの範囲で見たいか」で説明できます。

次章からは、最小のコードを実際に読む順番へ進みます。

各章のコードは、表示上の行番号を除いてコピーできます。

Leanは定義と証明の整合性、TLA+は有限モデルの状態遷移、PBTは実装を揺さぶったときの反例を扱います。三手法の価値は、保証の範囲を明示し、失敗を短い説明へ変えることにあります。

最初の対象は一つで十分です。対象・前提・性質・証拠を書き、反例を保存し、形式化しなかった部分を別のテストや運用へ渡してください。

用語集

保証
対象・前提・性質・証拠を伴う、範囲付きの主張。
証明支援系
証明を項として構築し、型検査で整合性を確認する系。ここではLean。
モデル検査
有限に切った状態空間を探索し、性質の違反トレースを探す方法。
Safety
悪い状態が決して到達しないという性質。
Liveness
公平性などの仮定の下で、良い状態へいつか進むという性質。
refinement
抽象仕様から実装へ、振る舞いの対応を保つこと。

理解度チェック

問1：PBTの「全ケース」とLeanの「全入力」はなぜ同じ意味ではないですか。
PBTはgeneratorが作った有限サンプル、Leanは形式化した型の全入力を対象にするためです。
問2：TLA+モデルの定数を一人にすると何が起きますか。
競合が消え、二人以上で起きる順序のバグを検査できなくなります。
問3：外部DBや時計を形式化しない場合、何をすべきですか。
未保証の境界を明記し、PBT・統合テスト・監視など別の証拠へ渡します。
問4：導入時に最初に選ぶべき対象は何ですか。
破ると高価で、最小の反例にできる性質です。
