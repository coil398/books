TLA+ 実践サンプル

Web・ゲーム・物理/数学を、状態変数・アクション・不変条件として読み解きます。

  • ゲームの手番・進行・取引を検査する

実例を読むための縮約

この章では、Web、ゲーム、物理・数学の状態をTLA+でモデル化します。抽象化とは、失敗モードに必要な状態だけを残して、実サービス全体を小さなモデルへ縮約することです。縮約したものと落としたものを毎回明記してください。

Shell
java -cp tla2tools.jar tlc2.TLC \
  -config Inventory.cfg Inventory.tla

モデルは、まず2ユーザー・容量1・短い履歴で検査します。反例を読める大きさにしてから、決済失敗、キャンセル、キャッシュ、切断を段階的に追加します。

実例ごとの三つの問い

何を保証したいか。なぜそれが必要か。破れると何が起きるか。コードの直前にこの三つを置くと、モデルの目的が実装の写経へ流れません。

Web例1：在庫引き当てと二重購入

保証したいのは、在庫が負にならず、購入済みの利用者が同じ商品を二重に確定しないことです。破れると欠品、返金、会計帳簿との不一致が起きます。

TLA+
---- MODULE Inventory ----
CONSTANT Users, InitialStock
VARIABLE stock, orders

Init == /\ stock = InitialStock
        /\ orders = [u \in Users |-> "none"]

Purchase(u) == /\ orders[u] = "none"
                /\ stock > 0
                /\ stock' = stock - 1
                /\ orders' = [orders EXCEPT ![u] = "paid"]

Next == \E u \in Users : Purchase(u)

TypeOK == /\ stock \in Nat
          /\ orders \in [Users -> {"none", "paid"}]

NoDouble == \A u \in Users : orders[u] = "none" \/ orders[u] = "paid"
Conserve == stock + Cardinality({u \in Users : orders[u] = "paid"}) = InitialStock

Spec == Init /\ [][Next]_<<stock, orders>>
========================================
TLC設定
CONSTANT Users = {"alice", "bob"}
CONSTANT InitialStock = 1
INVARIANT TypeOK
INVARIANT NoDouble
INVARIANT Conserve

`Conserve`は購入一件につき在庫を一つ消費する保存不変量です。決済失敗やキャンセルを追加するなら、予約・支払い・返金を状態として分けます。一つの`Purchase`に押し込むと、どの段階で在庫を戻すかが曖昧になります。

一アクションのatomicityを本番で再確認

モデルのPurchaseは判定・減算・注文更新が一つです。実装がSELECT、外部決済、UPDATEの三段階なら、同じ原子性を持たないので失敗アクションとPBTの競合テストを追加します。

Web例2：セッションとトークン失効

保証したいのは、失効済みトークンが再び有効にならないことです。破れると、ログアウトや強制失効がキャッシュ・認証ミドルウェアを通り抜けます。

TLA+
---- MODULE Session ----
CONSTANT Tokens
VARIABLE status

Init == status = [t \in Tokens |-> "valid"]

Revoke(t) == /\ status[t] = "valid"
             /\ status' = [status EXCEPT ![t] = "revoked"]

Use(t) == /\ status[t] = "valid"
          /\ UNCHANGED status

Next == \E t \in Tokens : Revoke(t) \/ Use(t)
TypeOK == status \in [Tokens -> {"valid", "revoked"}]
RevokedNeverValid == \A t \in Tokens :
  status[t] = "revoked" => status[t] # "valid"

Spec == Init /\ [][Next]_status
================================

`Use`を成功・失敗の観測変数として持ちたいなら、監査ログや応答状態を追加します。キャッシュ層が古い値を返す場合、`cache`を別変数にして、stale readを許す仕様と禁止する仕様を比較します。

「失効した」と「使えない」を分ける

保存状態がrevokedでも、別のAPI経路が古いセッションを使うなら、モデルの状態と実装の観測点がずれています。認証判定の全経路を契約へ含めます。

Web例3：リトライと冪等性

同じidempotency keyが何度届いても、残高や在庫への効果が一度だけであることを保証します。破れるとタイムアウト後の再送で二重請求が起きます。

TLA+
---- MODULE Idempotency ----
CONSTANT Keys
VARIABLE applied, balance

Init == /\ applied = {}
        /\ balance = 0

Apply(k) == /\ k \in Keys
            /\ k \notin applied
            /\ applied' = applied \cup {k}
            /\ balance' = balance + 1

Retry(k) == /\ k \in applied
            /\ UNCHANGED <<applied, balance>>

Next == \E k \in Keys : Apply(k) \/ Retry(k)
AtMostOnce == balance = Cardinality(applied)
Spec == Init /\ [][Next]_<<applied, balance>>
=============================================

ここでの`applied`は抽象的な集合です。本番のDB一意制約、トランザクション境界、同じキーで異なるpayloadが届いたときの契約は含みません。payloadを状態に加えると、「同じキーなら同じ内容」という性質も検査できます。

TLA+ / payload
VARIABLE requests, applied

Apply(k, payload) == /\ k \notin DOMAIN applied
                       /\ applied' =
                            [applied EXCEPT ![k] = payload]
                       /\ requests' = requests

キーの再利用を拒否するのか、元の結果を返すのか、409を返すのかはAPI仕様です。安全性として共通なのは、効果が一度だけという点です。

Web例4：キャッシュ整合性

「読める」と「最新版である」を分けます。強い整合性を要求するならcacheとoriginが一致すること、stale readを許すなら古さの上限や収束を別の性質にします。

TLA+
---- MODULE Cache ----
CONSTANT Values
VARIABLE origin, cache, version

Init == /\ origin = Values[1]
        /\ cache = origin
        /\ version = 0

Read == /\ cache' = cache
        /\ UNCHANGED <<origin, version>>

Write(v) == /\ v \in Values
            /\ origin' = v
            /\ cache' = v
            /\ version' = version + 1

StaleRead == /\ cache' = cache
             /\ UNCHANGED <<origin, version>>

Next == Read \/ (\E v \in Values : Write(v)) \/ StaleRead
Coherent == cache = origin
Spec == Init /\ [][Next]_<<origin, cache, version>>
===============================================

`StaleRead`を許せば`Coherent`は違反します。それがバグなのかeventual consistencyの契約なのかは、利用者が観測できる古さ、更新後の読み取り、無効化失敗の仕様で決まります。

抽象化の効き目

キャッシュを値一つにしたモデルはTTL・容量・ネットワークを表しませんが、読み書きの順序と「最新版」の定義をレビューできます。失った細部はPBTのfake clockや統合テストへ渡します。

ゲーム例1：ターン制の手番

現在の手番以外のプレイヤーが操作できないことを保証します。破れると同時入力の勝敗や得点が不正になります。プレイヤーが二人より多い場合は、次のプレイヤーを選ぶ関数を明示します。

TLA+
---- MODULE Turns ----
CONSTANT Players
VARIABLE turn, moves

Init == /\ turn = Players[1]
        /\ moves = 0

Play(p) == /\ p = turn
           /\ moves' = moves + 1
           /\ turn' = IF turn = Players[1]
                      THEN Players[2]
                      ELSE Players[1]

TypeOK == /\ turn \in Players
          /\ moves \in Nat
Next == \E p \in Players : Play(p)
Spec == Init /\ [][Next]_<<turn, moves>>
==============================================

手番だけでなく、入力が接続中か、ゲームが終了していないか、同じ操作IDが未処理かも状態です。最初のモデルは手番のSafetyに集中し、拡張時に新しい変数と不変量を追加します。

ゲーム例2：マッチングの進行

二人が待っているなら、いつかペアになるというLivenessを考えます。Safetyだけなら「待ち集合が壊れない」しか分かりません。公平性なしでは、Joinばかり選ばれてPairが永遠に選ばれない反例があり得ます。

TLA+
---- MODULE Match ----
CONSTANT Players
VARIABLE waiting, matched

Init == /\ waiting = {}
        /\ matched = {}

Join(p) == /\ p \in Players
           /\ p \notin waiting
           /\ p \notin matched
           /\ waiting' = waiting \cup {p}
           /\ UNCHANGED matched

Pair(a, b) == /\ a \in waiting
              /\ b \in waiting
              /\ a # b
              /\ matched' = matched \cup {{a, b}}
              /\ waiting' = waiting \ {a, b}

Next == (\E p \in Players : Join(p))
     \/ (\E a, b \in Players : Pair(a, b))

EventuallyPair == []((Cardinality(waiting) = 2)
  => <>(Cardinality(waiting) < 2))

Spec == Init /\ [][Next]_<<waiting, matched>>
============================================

実際のTLCでlivenessを検査するなら、アクションが有効なのに永遠に無視されないという公平性をモデルへ加えます。workerの公平なスケジュール、キューの順序、切断を一つずつ仮定として記録します。

公平性は実装の魔法ではない

WFを付けると不公平な実行を除外できますが、実装のスケジューラがその仮定を満たすかは別の証拠です。メトリクス、タイムアウト、負荷試験を残します。

ゲーム例3：アイテム取引の原子性

送信者からアイテムを削除し、受信者へ追加する操作を一つのアクションにします。半分だけ移った状態を許さないことが保証です。破れるとアイテム消失や複製が起きます。

TLA+
---- MODULE Trade ----
CONSTANT Players, Items
VARIABLE inventory, offers

Init == /\ inventory = [p \in Players |-> {}]
        /\ offers = {}

Offer(a, b, i) == /\ a # b
                  /\ i \in inventory[a]
                  /\ offers' = offers \cup
                       {[from |-> a, to |-> b, item |-> i]}
                  /\ UNCHANGED inventory

Accept(o) == /\ o \in offers
             /\ o.item \in inventory[o.from]
             /\ inventory' = [inventory EXCEPT
                    ![o.from] = @ \ {o.item},
                    ![o.to] = @ \cup {o.item}]
             /\ offers' = offers \ {o}

Next == (\E a, b \in Players, i \in Items : Offer(a,b,i))
     \/ (\E o \in offers : Accept(o))

Spec == Init /\ [][Next]_<<inventory, offers>>
===============================================

実装が二つのDB書き込みなら、モデルの原子性はありません。トランザクション、イベントソーシング、補償処理のどれを採用するかを仕様にし、途中状態を観測できるかをPBTと統合テストで検査します。

PlusCalと素のTLA+を比較する

PlusCal
---- MODULE LockPlusCal ----
VARIABLE lock

(* --algorithm Mutex
variables lock = "free";
process (P \in {"A", "B"})
begin
Acquire:
  await lock = "free";
  lock := self;
Critical:
  skip;
Release:
  lock := "free";
end process;
end algorithm; *)
================================
TLA+
---- MODULE LockRaw ----
CONSTANT Proc
VARIABLE owner

Init == owner = "free"
Acquire(p) == /\ owner = "free" /\ owner' = p
Release(p) == /\ owner = p /\ owner' = "free"
Next == \E p \in Proc : Acquire(p) \/ Release(p)
MutualExclusion == owner = "free" \/ owner \in Proc
Spec == Init /\ [][Next]_owner
================================

PlusCalは制御フロー、素のTLA+は状態関係を直接読ませます。変換後にAcquireの原子性、Releaseの所有者条件、process集合の定数設定を確認します。どちらもコメントや見た目だけでは証拠になりません。

物理・数学例1：離散化した保存量

離散積分の途中値が、閉形式の和と一致することを検査します。破れると、積分器の添字や更新順がずれます。連続系の誤差や浮動小数は別モデル・PBTの責任です。

TLA+
---- MODULE DiscreteSum ----
CONSTANT N
VARIABLE i, total

Init == /\ i = 0 /\ total = 0
Step == /\ i < N
        /\ i' = i + 1
        /\ total' = total + i'

Done == i = N
Invariant == total = i * (i - 1) / 2
Next == Step
Spec == Init /\ [][Next]_<<i, total>>
==============================================

`N`を自然数として与え、整数除算の意味を確認します。TLCは浮動小数の丸めを自動的に再現しないため、近似誤差の上限は実装側で別に検査します。

物理・数学例2：資源保存

複数エージェント間で資源を移動しても総量が保存されることを保証します。破れると会計残高や物理量が生成・消滅します。各エージェントの上限を保証するなら、別の不変条件が必要です。

TLA+
---- MODULE Conservation ----
EXTENDS Naturals

CONSTANT Capacity, Agents
VARIABLE resource

Init == resource = [a \in Agents |-> Capacity]

Move(a, b) == /\ a # b
              /\ resource[a] > 0
              /\ resource' = [resource EXCEPT
                    ![a] = @ - 1,
                    ![b] = @ + 1]

Total == Sum({resource[a] : a \in Agents})
Invariant == Total = Cardinality(Agents) * Capacity
Next == \E a, b \in Agents : Move(a, b)
Spec == Init /\ [][Next]_resource
===============================================

総量保存は一ステップの代数で説明できますが、マイナス禁止、上限、同時移動の公平性は別の性質です。どの不変量を「主」とし、どれを補助にするかを命名します。

物理・数学例3：ラウンドロビンの公平性

相互排除と順番の進行を一つのモデルで考えます。下の`Proc`は説明用のシーケンスです。実際のモデルでは、次要素を選ぶ関数を厳密に定義し、空集合や切断を扱います。

TLA+
---- MODULE RoundRobin ----
EXTENDS Sequences

CONSTANT Proc
VARIABLE turn, inCS

Init == /\ turn = Proc[1] /\ inCS = {}

Enter(p) == /\ p = turn
            /\ p \notin inCS
            /\ inCS' = inCS \cup {p}
            /\ UNCHANGED turn

Leave(p) == /\ p \in inCS
            /\ inCS' = inCS \ {p}
            /\ UNCHANGED turn

MutualExclusion == Cardinality(inCS) <= 1
Next == \E p \in Proc : Enter(p) \/ Leave(p)
Spec == Init /\ [][Next]_<<turn, inCS>>
==============================================

次のturnへ進むアクション、接続中のプロセス、待ち時間の上限を追加するとLivenessを検査できます。モデルで表していないインデックス操作を「完全なTLA+コード」と誤認させないため、教育用の範囲を明記します。

動かない断片を混ぜない

実際にTLCへ渡すファイルには、EXTENDS、定数、Init、Next、Spec、検査対象を揃えます。疑似コードを示す場合は、どの部分が未実装かをラベルで明記します。

モデルの境界を表にする

抽象化得られるもの失うもの引き渡し先
決済を一アクション二重請求の順序分断・部分成功PBTのfake・統合
キャッシュを値一つstale readの論理TTL・容量・再接続時計注入テスト
プレイヤー二人手番競合大規模マッチング負荷・モデル拡張
離散時間保存量・添字連続系の丸めPBTの許容誤差
集合で履歴所有権の総量順序・重複シーケンスモデル

境界は弱点の告白ではなく、証拠の設計図です。TLCの成功をCIログに残すときは、定数と抽象化の表も一緒に保存します。

実例から広げる課題

Web：キャンセルを追加する

TLA+
Cancel(u) == /\ orders[u] = "reserved"
             /\ orders' = [orders EXCEPT ![u] = "cancelled"]
             /\ stock' = stock + 1

支払い前のキャンセルと支払い後の返金は意味が違います。状態をreserved、paid、refundedなどに分け、保存不変量と台帳を別に置きます。

ゲーム：切断を追加する

TLA+
Disconnect(p) == /\ p \in Players
                 /\ connected' = connected \ {p}
                 /\ UNCHANGED turn

接続がないプレイヤーへ手番を渡さないSafetyと、接続中のプレイヤーへいつか進むLivenessを分けます。切断・再接続・タイムアウトの順序が反例を変えます。

モデル品質のチェックリスト

  • 仕様の一アクションを日本語で説明できる。
  • 初期状態が空でなく、Nextに通常遷移がある。
  • TypeOKと業務不変条件を分けている。
  • 更新しない変数にUNCHANGEDがある。
  • 定数が競合を消していない。
  • 順序が必要な履歴を集合にしていない。
  • Livenessの公平性を実装の仮定として説明できる。
  • 抽象化で失った性質をPBTへ記録した。

反例が十個出たら、同じ原因を分類してから修正します。モデル検査が終わらないときは、変数を増やす前に抽象化と観測範囲を見直します。

まとめ

Webでは原子性・冪等性・整合性、ゲームでは手番・所有権・進行、物理・数学では保存量・離散化・公平性をモデル化しました。TLA+の実例は、設計判断を短い反例へ変換する練習です。

次章では、同じ失敗を実装の入力・操作列としてPBTへ渡します。

用語集

冪等性
同じ操作を繰り返しても効果が一度だけ、または結果が変わらない性質。
整合性
複数の状態や表現が、要求された関係を保つこと。
原子アクション
途中状態を分割せず一つの遷移として扱う操作。
stale read
キャッシュなどから古い値を読むこと。
補償処理
分割された処理の一部が成功した後、意味を戻すための処理。
抽象化境界
モデル化した範囲と、別の証拠へ渡した範囲の境目。

理解度チェック

問1：在庫モデルのConserveは何を保証しますか。
購入済みの件数と残在庫の合計が初期在庫に等しいことです。
問2：キャッシュモデルでStaleReadを許すと何が変わりますか。
cacheとoriginの一致は常に成立しなくなり、最新版性を別の性質にする必要があります。
問3：ゲームのLivenessを検査するのに公平性が必要になる理由は何ですか。
Pairや次の手番が有効でも永遠に選ばれない実行を除外するためです。
問4：物理の離散TLA+モデルが浮動小数の丸めを保証しないのはなぜですか。
整数・有限状態の抽象モデルであり、実装の数値表現や誤差を含めていないためです。
