Chapter 03 · 形式手法とテスト技法

TLA+ / PlusCal / TLC の基礎

状態とアクションをモデルにし、競合・保存・進行性を有限範囲で検査します。

対象分散・並行システムを設計するエンジニア
成果物小さなTLA+モデルとTLC設定を書ける
読む目安70〜100分

この章で学ぶこと

  • Init・Next・Specの関係
  • TypeOK・Safety・Livenessの違い
  • PlusCalとTLCの実行・状態爆発対策

前提知識

  • 変数・集合・論理式
  • 並行実行の順序
  • 有限モデルの考え方

所要時間の目安

2ユーザー・容量1の反例を手で追い、SafetyとLivenessを分けます。

状態とアクション

TLA+では、システムを値の組として表す状態と、状態から次状態への関係で表します。アクションの中でプライム記号`'`を使うと、次の状態の値を書けます。プログラムの行順を写すより、何が一つの原子操作かを決めることが重要です。

TLA+
---------------- MODULE Counter ----------------
VARIABLE count

Init == count = 0
Inc == count' = count + 1
Next == Inc
Spec == Init /\ [][Next]_count
===============================================

`Init`は初期状態、`Next`は一ステップの遷移、`Spec`は実行全体の仕様です。`[][Next]_count`はNextが起きるか、観測変数countが変わらないstutteringを許します。

先に日本語でアクションを書く

「購入を一件確定し、在庫を一つ減らす」「監査ログだけを追加し、残高は変えない」のように一文で言えないアクションは、まだモデルの粒度が決まっていません。

TypeOKと不変条件

不変条件は、初期状態から到達できる全状態で成立してほしい述語です。`TypeOK`は値の形を、業務不変条件は保存・所有権・上限を表します。

TLA+
---------------- MODULE CounterType ----------------
EXTENDS Naturals
VARIABLE count

Init == count = 0
Inc == count' = count + 1
Next == Inc
TypeOK == count \in Nat
Bound == count <= 10
Spec == Init /\ [][Next]_count
=======================================================

TLCはモデルの状態を探索し、違反時に初期状態からのトレースを出します。`TypeOK`だけでは、在庫が負でない、二人が同じロックを持たない、台帳と残高が一致する、といった業務性質は保証しません。

TLA+ / Safety
Safety == [] (count >= 0)
Progress == <> (count > 0)

Safetyは「悪い状態が起きない」、Livenessは「良い状態へいつか進む」です。Livenessには公平性、停止条件、環境の仮定が必要です。まずSafetyの反例を読めるモデルを作り、その後に進行性を追加します。

論理演算子とアクションの形

記法意味実務での確認
`/\`かつ一つの遷移に必要な前提と更新を束ねる
`\/`または別のアクションを選択する
`'`次状態更新する変数をすべて書く
`UNCHANGED x`xは不変意図しない非決定性を防ぐ
`[]`常にSafetyの時間演算子
`<>`いつかLivenessの時間演算子
`WF_vars(A)`弱公平性有効なAが永遠に選ばれない実行を除く
TLA+
VARIABLES stock, log

Init == /\ stock = 1
        /\ log = <<>>

Audit == /\ log' = Append(log, "audit")
          /\ UNCHANGED stock

Spec == Init /\ [][Audit]_<<stock, log>>

アクションで更新しない変数を暗黙に残すと、TLA+の意味上は意図しない変化が許されることがあります。`UNCHANGED`は「変えない」という契約をコードに残します。

集合・関数・シーケンス

集合は順序を持たず、関数は引数から値への対応、シーケンスは順番を持つ列です。ユーザー集合を使うと存在量化でプロセスを選べます。キューのFIFOを表したいなら集合ではなく`Sequences`を使います。

TLA+
---------------- MODULE Lock ----------------
CONSTANT Users
VARIABLE owner

Init == owner = [u \in Users |-> "free"]

Claim(u) == /\ owner[u] = "free"
            /\ owner' = [owner EXCEPT ![u] = "claimed"]

Release(u) == /\ owner[u] = "claimed"
              /\ owner' = [owner EXCEPT ![u] = "free"]

Next == \E u \in Users : Claim(u) \/ Release(u)
TypeOK == owner \in [Users -> {"free", "claimed"}]
Spec == Init /\ [][Next]_owner
===============================================
TLA+ / Sequence
---------------- MODULE Queue ----------------
EXTENDS Naturals, Sequences
VARIABLE queue

Init == queue = <<>>
Enqueue(x) == queue' = Append(queue, x)
Dequeue == /\ Len(queue) > 0
           /\ queue' = Tail(queue)
QueueType == queue \in Seq(Nat)
Spec == Init /\ [][Enqueue(1) \/ Dequeue]_queue
===============================================

関数更新は元の関数を破壊せず、新しい関数を作ります。`@`は更新前の値です。キーが存在する前提や、空キューでDequeueを呼べない条件を`Next`に含めるか、TypeOKで監視するかを決めます。

TLA+
VARIABLE table

Put(k, v) == table' = [table EXCEPT ![k] = v]
Increment(k) == table' = [table EXCEPT ![k] = @ + 1]

Specを正しく閉じる

観測対象の変数を`vars == <<...>>`へまとめ、Specのstuttering対象に含めます。変数が漏れると、その変数だけ自由に変わる状態をTLCが許し、検査結果を誤解しやすくなります。

TLA+
---------------- MODULE Pair ----------------
VARIABLES x, y
vars == <<x, y>>

Init == /\ x = 0
        /\ y = 0

Step == /\ x' = x + 1
        /\ y' = y + x'

TypeOK == /\ x \in Nat
          /\ y \in Nat

Spec == Init /\ [][Step]_vars
===============================================

一アクションがDBトランザクションに対応するなら、実装でも同じ範囲がatomicityを持つか確認します。モデル上は一行でも、実装では複数SQLや外部APIを含むなら、失敗・リトライ・タイムアウトを別アクションに分けます。

モデルの簡略化を隠さない

決済を一アクションにしたなら、ネットワーク分断と部分成功をモデル化していません。失った性質を表に書き、PBTや統合テストへ引き渡します。

TLCを回す

TLCはTLA+仕様に具体的な定数を与え、有限状態を探索するモデルチェッカーです。Toolboxやエディタ拡張から実行できますが、CIでは同じモデルと設定をコマンドで再現できるようにします。

Shell
java -cp tla2tools.jar tlc2.TLC \
  -config Counter.cfg Counter.tla
TLC設定の例
CONSTANT Users = {"alice", "bob"}
INVARIANT TypeOK
INVARIANT Safety
PROPERTY Progress

設定を変更せずにモデルだけを変えると、何を検査したかが不明になります。成功ログにはモデル名、定数、検査したinvariant、TLCの版、実行日時を残します。

確認なぜ必要か欠けたとき
Initが実行可能開始状態が存在する0状態や即時エラーを成功と誤認
Nextに通常遷移がある実行列が進む停滞しかないモデルになる
定数が競合を含む並行性を観測できる一人モデルで穴が消える
監視変数がSpecに含まれる変化を追跡できるstutteringで自由に動く
期待する反例サイズを決める短いトレースを読める状態爆発に気づかない

PlusCalから入る

PlusCalは、プロセスと逐次的な見た目でアルゴリズムを書く記法です。変換後の意味はTLA+なので、生成されたTLA+のアクション・所有者条件・UNCHANGEDを必ず読みます。

PlusCal
---- MODULE MutexPlusCal ----
VARIABLE lock

(* --algorithm Mutex
variables lock = "free";
process (P \in {"A", "B"})
begin
Acquire:
  await lock = "free";
  lock := self;
Critical:
  skip;
Release:
  lock := "free";
end process;
end algorithm; *)
================================

PlusCalは人間の制御フローを整理する入口、素のTLA+は集合・関係・時間演算子を直接書く出口です。変換後に`Acquire`が本当に一つの原子アクションか、`Release`が所有者だけに許されるかを検査します。

PlusCalの見た目に安心しない

逐次プログラムのように見えても、複数processのinterleavingは存在します。コメントブロックを保存しただけでは証拠にならず、変換・モデル設定・invariantまで再現します。

状態爆発を制御する

クライアント数、キュー長、再試行回数、履歴の長さは状態数を積で増やします。最小反例が目的なら、2プロセス・容量1・短い履歴から始めます。小さくする理由と一般化できる理由を別々に記録します。

対策方法失う可能性
対称性同型のプロセスを同一視IDに意味がある監査・権限
抽象化金額をカテゴリへ閾値・丸め・細かな順序
小さな定数2人・容量1から開始大規模固有の組合せ
履歴の圧縮集合・カウンタにする重複・順序・再配信
Safety優先まず不変条件進行性のバグ

抽象化は「バグを消す」こともあります。キューを集合に変えるとFIFOの逆転が観測できません。履歴をカウンタにするなら、順序が不要なことを要求とレビューで確認します。

反例を読む

TLCの反例では、違反状態だけでなく、そこへ至ったアクションの順序を読みます。どの前提が同時に満たされ、どの変数更新が同じアクションに入っていなかったかを確認します。

反例トレース
State 1: stock = 1, reserved = {}
Action: Reserve("alice")
State 2: stock = 0, reserved = {"alice"}
Action: Reserve("bob")
State 3: stock = -1, reserved = {"alice", "bob"}

この例では、予約前の`stock > 0`が抜けたか、判定と更新のatomicityが抜けています。実装のロックを議論する前に、仕様の一アクションを直します。反例の状態列は修正後もfixtureや設計資料として保存します。

TLA+ / Conservation
CONSTANT Capacity, Users
VARIABLES available, held

Init == /\ available = Capacity
        /\ held = [u \in Users |-> 0]

Take(u) == /\ held[u] < 1
           /\ available > 0
           /\ available' = available - 1
           /\ held' = [held EXCEPT ![u] = @ + 1]

Return(u) == /\ held[u] = 1
             /\ available' = available + 1
             /\ held' = [held EXCEPT ![u] = 0]

Next == \E u \in Users : Take(u) \/ Return(u)
TypeOK == /\ available \in Nat
          /\ held \in [Users -> {0, 1}]
Conservation == available + Sum({held[u] : u \in Users}) = Capacity
Spec == Init /\ [][Next]_<<available, held>>

保存不変量は、個々の操作が正しそうに見えるだけでは見つからない漏れを検出します。Returnの前提、初期値、二重取得を一つずつ壊して、どの短い反例になるかを学びます。

Livenessと公平性

TLA+
---------------- MODULE Turn ----------------
VARIABLE turn

Init == turn = "alice"
Next == turn' = IF turn = "alice" THEN "bob" ELSE "alice"
Fairness == WF_<<turn>>(Next)
Spec == Init /\ [][Next]_turn /\ Fairness
===============================================

`WF_vars(A)`は、アクションAが継続的に有効ならいつか実行されるという弱公平性です。永遠に一人だけが選ばれない実行を除外できますが、実装のスケジューラが本当に公平である証拠ではありません。

TLA+ / Progress
VARIABLE status

Init == status = "waiting"
Complete == /\ status = "waiting"
            /\ status' = "done"
EventuallyDone == <> (status = "done")
Spec == Init /\ [][Complete]_status
Livenessの仮定を書き残す

ネットワークがいつか回復する、workerが公平に選ばれる、外部サービスが有限時間で返す、といった前提がないと、進行性の主張は過剰になります。

段階的にモデルを拡張する

  1. 段階A：状態と一つの通常アクションだけを書く。
  2. 段階B：TypeOKで値の形を固定する。
  3. 段階C：Safety不変条件と保存を追加する。
  4. 段階D：失敗、再試行、キャンセルを追加する。
  5. 段階E：livenessと公平性を追加する。
  6. 段階F：タイムアウト、分断、キャッシュの抽象化を見直す。

最初からすべての障害を入れると、反例の意味が読めなくなります。各段階で「何を追加したか」「何をまだ落としているか」「新しい反例がどの設計判断を示すか」を変更記録に残します。

レビュー質問
Initはどこから始まるか
Nextの一回は何を意味するか
更新しない変数はUNCHANGEDか
TypeOKと業務不変条件は分かれているか
モデルの原子性は実装の境界と対応するか
公平性は環境のどんな仮定か

練習問題

次の問題は、先に日本語で性質を書き、その後にInit・Next・TypeOK・主不変条件・定数設定・期待する反例を作ります。

  • 容量2のキューが負の長さにならない。
  • 同じ利用者が二つのロックを同時に持たない。
  • 期限切れセッションが更新されない。
  • 二人のゲームで手番でない人が得点しない。
  • 冪等キーの再送で残高が二重に増えない。
提出形式
モデル名:
定数:
Init:
Next:
TypeOK:
Safety:
Livenessと公平性:
TLCの期待結果:
抽象化して失った性質:

仕様を書く人とは別の人が、実装を見ずに`Init`と`Next`を説明できるか確認します。説明できない仕様は、実装の写経か、抽象化が過剰です。

まとめ

TLA+の本体は記法の暗記ではなく、状態・アクション・原子性・不変条件・公平性の選び方です。小さな定数で短い反例を作り、成功結果にもモデルの範囲を添えます。

次章では在庫、セッション、ゲーム、保存量の実例を通じて、抽象モデルが何を表し、何を落とすかを確認します。

用語集

状態
状態変数の現在値を組にした、システムのスナップショット。
アクション
現在状態と次状態の関係を表す式。
stuttering
観測変数が変わらないまま進む、または停止するステップ。
TypeOK
変数が想定した型・集合に属するという不変条件。
公平性
有効なアクションやプロセスが永遠に無視されないという仮定。
状態爆発
変数やプロセスを増やすと状態数が組合せ的に増える現象。

理解度チェック

問1：`Init`、`Next`、`Spec`をそれぞれ説明してください。
Initは初期状態、Nextは一ステップの遷移、Specは実行全体です。
問2：`UNCHANGED`を明示する理由は何ですか。
更新しない変数に意図しない変化を許さず、アクションの粒度を明確にするためです。
問3：SafetyとLivenessの反例はどう違いますか。
Safetyは有限の違反トレース、Livenessは停滞や無限に進まない実行です。
問4：TLCの定数を小さくする際、何を記録すべきですか。
何を失ったか、なぜ最小反例として十分か、実装へどう引き渡すかです。
