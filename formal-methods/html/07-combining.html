Chapter 07 · 形式手法とテスト技法

Lean・TLA+・PBTを組み合わせる

ECの購入フローを題材に、設計・実装・計算を三つの証拠で一気通貫に結びます。

対象各基礎章を読み、統合の境界を知りたいチーム
成果物同一題材の保証分担を設計できる
読む目安80〜120分

この章で学ぶこと

  • 在庫・冪等性をTLA+で設計する
  • 操作列・競合をPBTで再現する
  • 金額計算をLeanで固定しCIへ分離する

前提知識

  • Lean・TLA+・PBTの基礎章
  • ECの注文・決済の概念
  • CIジョブとfixtureの運用

所要時間の目安

TLA+の反例をPBTへ移し、Leanの定理と移植propertyを対応づけます。

一つの題材を三層に分ける

題材は、在庫を持つECの購入フローです。注文、決済、再試行、返金、明細計算が混ざるため、保証分担（一つの主張を複数の手法の適切な範囲へ割り当てること）を設計する練習に向いています。

層保証したい性質技術証拠の形
プロトコル在庫は負にならないTLA+Safetyの検査・反例
プロトコル冪等キーの効果は一度だけTLA+ / PBT状態列・操作列
実装境界JSONの往復・入力検証PBT縮小入力・fixture
計算小計・割引の恒等式Lean / PBT定理・移植property
外部依存決済遅延・失敗・タイムアウトPBT fake観測された呼出し

「すべてを一つの道具で」は狙いません。各層の証拠が何を保証し、何を保証しないかを対応表にしてからコードを書きます。

一気通貫の完了条件

TLA+の反例をPBTの操作列へ変換でき、Leanの定理と実装の計算関数の対応を説明でき、CIで三つの結果を別々に保存できれば、統合の骨格ができています。

TLA+で設計する

まず利用者二人、在庫一個、注文キー二つに縮約します。冪等キーは同じ要求の再送を同じ効果として識別するキーです。購入の判定・在庫減算・注文記録・キー記録を一アクションとし、再送は状態を変えないアクションにします。

TLA+
---- MODULE Shop ----
CONSTANT Users, Keys, InitialStock
VARIABLE stock, orders, applied

Init == /\ stock = InitialStock
        /\ orders = [u \in Users |-> "none"]
        /\ applied = {}

Purchase(u, k) == /\ u \in Users
                  /\ k \in Keys
                  /\ orders[u] = "none"
                  /\ k \notin applied
                  /\ stock > 0
                  /\ stock' = stock - 1
                  /\ orders' = [orders EXCEPT ![u] = "paid"]
                  /\ applied' = applied \cup {k}

Retry(k) == /\ k \in applied
           /\ UNCHANGED <<stock, orders, applied>>

Next == (\E u \in Users, k \in Keys : Purchase(u, k))
     \/ (\E k \in Keys : Retry(k))

TypeOK == /\ stock \in Nat
          /\ orders \in [Users -> {"none", "paid"}]
          /\ applied \subseteq Keys

Safety == stock >= 0
AtMostOnce == Cardinality({u \in Users :
  orders[u] = "paid"}) <= InitialStock

Spec == Init /\ [][Next]_<<stock, orders, applied>>
==============================================

ここで保証するのは、指定した有限集合とアクション粒度です。DBのトランザクション分離、決済サービスの部分成功、キーとpayloadの不一致は、次のモデル拡張かPBTへ渡します。

TLC設定
CONSTANT Users = {"alice", "bob"}
CONSTANT Keys = {"k1", "k2"}
CONSTANT InitialStock = 1
INVARIANT TypeOK
INVARIANT Safety
INVARIANT AtMostOnce

在庫を1にするのは一般性を捨てるためではなく、二人が同時購入できる最小の競合を作るためです。反例が説明できたら、在庫2や3人へ増やします。

反例を読む

誤った仕様で`stock > 0`を外すと、二人の購入が在庫を使い切った後も進みます。違反状態だけでなく、どのアクションが保存不変量を壊したかを読んでください。

TLCの反例
State 1: stock = 1
         orders = [alice |-> "none", bob |-> "none"]
Action: Purchase("alice", "k1")

State 2: stock = 0
         orders = [alice |-> "paid", bob |-> "none"]
Action: Purchase("bob", "k2")

State 3: stock = -1
         orders = [alice |-> "paid", bob |-> "paid"]

この反例は、実装のif文を一行足すだけでなく、判定と減算をどのトランザクションが占有するかを直す資料です。モデルの修正後は、同じトレースが禁止された理由をコミットメッセージや設計記録に残します。

反例を仕様に合わせて消さない

実装が負の在庫を許すからといってSafetyを弱めると、検査が通る代わりに要求を失います。要求を変更したなら、保存不変量と返金・欠品の契約も一緒に更新します。

TLA+の契約をPythonへ渡す

Python / educational implementation
from dataclasses import dataclass


@dataclass(frozen=True)
class Order:
    user: str
    key: str
    status: str = "paid"


class Shop:
    def __init__(self, stock: int):
        self.stock = stock
        self.orders: dict[str, Order] = {}
        self.applied: set[str] = set()

    def purchase(self, user: str, key: str) -> bool:
        if key in self.applied:
            return True
        if user in self.orders or self.stock <= 0:
            return False
        self.stock -= 1
        self.orders[user] = Order(user, key)
        self.applied.add(key)
        return True

これは単一スレッドの教育用実装で、DBトランザクションを表しません。本番ではstockの条件付き更新と注文の一意制約を同じ原子性へ置き、外部決済の結果を状態機械に接続します。

TLA+の要素Pythonの観測点未保証の部分
stockshop.stockDBの同時更新
ordersshop.orders永続化・再起動
appliedshop.applied一意制約・キーpayload
Purchasepurchase()トランザクション境界
Retry同じkeyの再呼出しHTTP応答方針

PBTで操作列を生成する

TLA+と同じ小さな値域で実装を操作し、在庫・注文・適用キーの関係を確認します。PBTは辞書の更新順や同じキーの再送を混ぜ、接続ミスを見つけます。

Python / Hypothesis
from hypothesis import given, strategies as st


users = st.sampled_from(["alice", "bob", "carol"])
keys = st.sampled_from(["k1", "k2", "k3"])
actions = st.lists(st.tuples(users, keys), max_size=30)


@given(actions)
def test_shop_never_over_sells(actions):
    shop = Shop(1)
    for user, key in actions:
        shop.purchase(user, key)

    assert shop.stock >= 0
    assert len(shop.orders) <= 1
    assert len(shop.applied) <= 1

このpropertyは単一スレッドの順序を調べます。実際の競合を調べるには、インターリーブ可能なfakeやDBの条件付き更新を使います。並行性を逐次操作に置き換えたことで何を失ったかを記録します。

同じキーの効果を一度だけにする

Python / Hypothesis
@given(users, keys)
def test_same_key_has_one_effect(user, key):
    shop = Shop(1)

    first = shop.purchase(user, key)
    stock_after_first = shop.stock

    second = shop.purchase(user, key)

    assert first is True
    assert second is True
    assert shop.stock == stock_after_first
    assert len(shop.orders) <= 1

再送時にTrueを返すか409を返すかはAPI契約の選択です。共通に必要なのは、同じキーの効果が二度発生しないことです。結果を返す設計なら、最初のレスポンスが保存されていることもモデルに追加します。

競合をfakeで再現する

判定とcommitが分離した実装を、二つのスレッドの代わりに手動インターリーブで再現します。これは修正版ではなく、TLA+の競合を実装粒度で再現するための教材です。

Python / race fixture
class NonAtomicShop:
    def __init__(self):
        self.stock = 1
        self.pending: list[str] = []

    def check(self) -> bool:
        return self.stock > 0

    def commit(self, user: str):
        self.stock -= 1
        self.pending.append(user)


def test_interleaving_exposes_race():
    shop = NonAtomicShop()

    assert shop.check()
    assert shop.check()

    shop.commit("alice")
    shop.commit("bob")

    assert shop.stock == -1

本番修正後は、同じシナリオが失敗する（つまり在庫が負にならない）ことを確認します。SQLの条件付きUPDATE、行ロック、serializable transactionなど、採用したatomicityをテストの名前と設計文書に置きます。

競合fixtureを本番コードの代わりにしない

race fixtureは欠陥を示すための最小反例です。これが通ることを品質基準にせず、修正版の公開APIとDB境界へ同じ意味のpropertyを移します。

Leanで金額の中核を切り出す

ECの金額計算から、外部依存のない小計と割引を切り出します。Leanは全入力の定理、PBTは移植実装との接続、TLA+は注文の順序を担当します。

Lean 4
import Mathlib

def subtotal (prices : List Nat) : Nat :=
  prices.sum

def discount (amount rate : Nat) : Nat :=
  amount * rate / 100

def total (prices : List Nat) (rate : Nat) : Nat :=
  subtotal prices - discount (subtotal prices) rate

theorem subtotal_nonnegative (prices : List Nat) :
    0 <= subtotal prices := by
  exact Nat.zero_le _

theorem subtotal_append (xs ys : List Nat) :
    subtotal (xs ++ ys) = subtotal xs + subtotal ys := by
  simp [subtotal]

保証したいのは、明細を分割して集計しても小計が変わらないことです。返品、税、通貨、丸めを追加するなら、同じ定義へ押し込まず、別の仕様と前提を持つ関数・定理にします。

Lean 4 / bounded discount
import Mathlib

structure Percent where
  value : Nat
  bound : value <= 100

def boundedDiscount (amount : Nat) (rate : Percent) : Nat :=
  amount * rate.value / 100

theorem boundedDiscount_le (amount : Nat) (rate : Percent) :
    boundedDiscount amount rate <= amount := by
  unfold boundedDiscount
  omega

rateの範囲をvalidatorに任せる代わりに型へ埋め込むと、boundedDiscountの呼び出し側に前提が残ります。型を作る境界が本当に全API入口を覆うことは、PBT・レビューで確認します。

Leanの定理と移植実装を接続する

Leanの`subtotal`とPythonの`python_subtotal`が同じ仕様だと、名前だけでは分かりません。Python側で、Leanの定理と同じ関係をpropertyとして再実装します。これは定理の再証明ではなく、移植境界の経験的な接続証拠です。

Python / port property
from hypothesis import given, strategies as st


def python_subtotal(prices: list[int]) -> int:
    return sum(prices)


@given(
    st.lists(st.integers(min_value=0), max_size=100),
    st.lists(st.integers(min_value=0), max_size=100),
)
def test_python_subtotal_append(xs, ys):
    assert python_subtotal(xs + ys) == (
        python_subtotal(xs) + python_subtotal(ys)
    )
Leanが固定するPBTが接続するまだ別途必要
List Natの小計恒等式Pythonのリスト・整数固定幅・DB Decimal
rate<=100の割引上限API入力のgenerator税・通貨・丸め仕様
型の不正状態排除serialize/deserializeHTTP middleware
純粋関数の結果実装の観測値ネットワーク・時計
移植propertyを証明と呼ばない

有限サンプルの移植確認は、Leanの全入力定理を置き換えません。逆に、Leanの定理だけではPython実装のバグを検出できません。二つを別の証拠として報告します。

どこまで形式化するか

対象LeanTLA+PBT
小計・割引定理の中心通常は不要移植・境界
在庫競合不向き中心実装再現
JSON型の補助抽象化次第往復・拒否
DB障害抽象化が大きい失敗アクションfake・統合
UI通常は対象外通常は対象外E2E・例示

境界は固定ではありません。高価な性質、再利用される性質、過去に反例が出た性質から深くします。形式化しないことは無視ではなく、別の担当へ明示的に渡すことです。

境界の記録
TLA+:
  状態、競合、原子性、冪等性、進行性

PBT:
  API、JSON、時計、外部fake、操作列

Lean:
  小計、割引、単位、権限、純粋なデータ変換

未保証:
  実DBの分離、ネットワーク、UI、負荷、運用時計

段階的な導入ロードマップ

  1. 要求変更や過去障害から、保証したい性質を文章にする。
  2. PBTをCIへ置き、入力境界と実装の反例を集める。
  3. TLA+で二人・在庫一個・キー二つの最小モデルを検査する。
  4. Leanで丸め・割引・集計など純粋な計算核を固定する。
  5. 変更レビューで、三つのどの証拠を更新するか確認する。
CIジョブの分離
jobs:
  tla:
    steps:
      - run: java -cp tla2tools.jar tlc2.TLC -config Shop.cfg Shop.tla
  lean:
    steps:
      - run: lake build
  pbt:
    steps:
      - run: pytest -q

ジョブを分けると、どの保証が失敗したかが明確になります。成功ログにはTLCの定数、Leanのtoolchain、PBTの例数とprofileを記録します。

チームへ導入するときの言葉

ツール名ではなく、過去障害と最小反例で説明します。「二重請求をゼロにする」と断言せず、「二人・在庫一個のモデルでstockが負にならないことをPRごとに検査する」と範囲を言います。

失敗証拠の形修正先
TLA+ Safety違反状態トレーストランザクション設計
TLA+ Liveness違反停滞・無限待ちスケジューラ・公平性
PBT失敗縮小入力・操作列実装・fixture
Lean失敗未解決ゴール定義・前提

証明を書く担当者だけでなく、反例を修正する担当者を決めます。最初の成功は、短い反例が本番障害の原因説明になったときです。

導入を止めないルール

一つのPRで三つのツールを同時に導入せず、まず過去障害を一件だけ再現します。証明できない外部要素は隠さず、テストの担当として記録します。

変更時のレビュー質問

質問見る場所見落とすと
新しい状態はあるかTLA+変数・TypeOK状態不変条件が抜ける
新しい順序はあるかNext・liveness競合や無限待ちが抜ける
金額の恒等式は変わるかLean theorem丸め・前提が古くなる
入力境界は増えたかPBT generator未知・最大値が抜ける
反例を再現できるかfixture・seed修正が退行する
未形式化の依存は何かfake・統合成功範囲を誤認する
変更の流れ
要求変更
  -> 不変条件を更新
  -> TLA+の遷移と定数を更新
  -> 最小モデルを検査
  -> PBTの操作とJSONを更新
  -> Leanの関数と定理を更新
  -> CIで三つの証拠を再生成

どれか一つだけ更新すると、仕様と実装が静かに乖離します。変更PRには、更新した証拠・範囲が変わらない証拠・未更新の理由を分けて書きます。

統合で起きる失敗

仕様を実装の写経にする

TLA+のモデルもPBTのモデルも、実装の分岐をそのままコピーしないでください。独立した抽象化と小さなオラクルを置きます。

定数を一つにして競合を消す

最小モデルは2人・容量1から始めます。一人モデルの成功は、同時購入の設計を覆いません。

Leanと本番コードが乖離する

定義の対応表、移植property、固定fixtureを置きます。手書き移植はrefinementの穴になり得ます。

flaky retryを完了扱いしない

seed、縮小入力、TLCトレース、Leanの未証明ゴールをartifactとして残し、再実行だけで失敗を隠さないようにします。

最終チェックリスト

  • TLA+の状態変数が実装状態に対応している。
  • 一アクションのatomicityが明示されている。
  • PBTが同一キー・空入力・境界値を生成する。
  • shrink済みの反例が保存されている。
  • Leanの定義と移植実装の対応が明記されている。
  • sorryやflaky retryを完了の証拠にしていない。
  • 形式化しない部分が別テスト・監視で覆われている。
  • チームが保証範囲を一文で説明できる。

統合の価値はツールの数ではなく、設計の順序、実装の入力、計算の全域性を最も適した証拠へ結びつけることです。

まとめ

TLA+が同時実行の穴を探し、PBTが実装の境界を揺さぶり、Leanが純粋な計算の核を全入力で固定します。三つの成功は別々に報告し、対応表でつなぎます。

最初は過去障害を一件だけ選び、最小モデル・最小反例・最小定理を作ります。反例を回帰資産に変え、仕様変更のたびに三つの証拠のどれが動くかをレビューしてください。

用語集

縦切り
一つの題材を設計・実装・計算などの層へ分けて、端から端まで扱うこと。
冪等キー
同じ要求の再送を同じ効果として識別するキー。
refinement
抽象モデルの振る舞いと具体実装の対応。
移植property
定理と別言語の実装が同じ関係を持つかを経験的に確認するproperty。
fixture
反例や既知の入力を固定したテストデータ。
保証分担
一つの品質主張を複数の手法の適切な範囲へ割り当てること。

理解度チェック

問1：同じ購入フローでTLA+が担当するものは何ですか。
在庫競合、状態遷移、冪等性、原子性、進行性などのプロトコルです。
問2：PBTがTLA+の反例を操作列へ移す価値は何ですか。
抽象モデルで見つけた順序を、実装の型・API・fakeで再現できるためです。
問3：Leanのsubtotal定理は何を保証し、何を保証しませんか。
純粋な小計の恒等式を保証しますが、DB・決済・手書き移植・HTTP経路は保証しません。
問4：統合CIのジョブを分ける理由は何ですか。
どの層の保証が失敗したか、モデル定数やtoolchainの範囲を分けて読めるためです。
